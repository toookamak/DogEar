# 01. 产品定义

## 1.1 定位

**DogEar（折耳书签）** 是一个以书签为核心的个人网页信息收集与管理工具。

它的核心目标是降低网页保存成本，并通过场景化整理、自动信息提取和快速检索，让大量长期积累的书签仍然容易找到和重新发现。

Snapshot 等内容归档能力用于提高书签的长期可靠性，而不是将产品转变为阅读或知识管理工具。

> **操作口径：低成本 Capture + 场景化 Organize + 低成本 Rediscover**
>
> **先收藏，不急着整理；系统帮助理解和分流，之后再决定怎么管理。**
>
> 更简单地说：**先存下来，剩下的以后再说。**

- 三个核心问题：

  1. **好存（Capture）**：在电脑、浏览器、AI 对话等当前优先场景中，都能低成本保存链接；用户不需要在收藏时立即决定分类、标签、文件夹、是否值得阅读。保存动作尽可能接近"零成本"。**本版不优先手机 / Share Extension**（见 §1.4、附录 B）。

  2. **好管理（Organize）**：不依赖用户长期维护复杂的文件夹和标签体系；系统理解书签的用途与上下文，辅助用户进行**场景化分流**；用户按自己的实际需求管理，而非被固定信息架构限制。

  3. **好找 / 好重新发现（Rediscover）**：收藏之后不能因进入数据库就"消失"；用户应能通过搜索、场景、最近收藏、历史访问、长期资料、相关内容等重新发现过去收藏的内容。

- **不依赖 Raindrop 即可完整使用。** 应用数据始终为真源。Raindrop、S3、WebDAV 等是**数据管理选项**（输入源和/或导出/备份方向），不是登录门槛。首次使用**不引导登录 Raindrop**，只引导用户做数据管理选择（可跳过、可稍后），见 §3.0。

- **核心框架最小集**：工作台能保存 + Agent（Skill）能保存。页面保存属于工作台。浏览器插件保存不作为过关条件。
- 支持通过多种入口保存书签（工作台页面、Agent、浏览器插件；其他 App 非核心）。

- 归档能力中，**Snapshot（网页快照）是"网页内容长效保全"层**；Reader（清洗阅读版）及关联能力为**远期规划**（见[附录 B：Roadmap（产品分期）](#附录-broadmap产品分期)），按需逐步丰富。当前产品不依赖阅读闭环运转。

- **数据采用分层存储**：结构化数据与内容数据分开存放，结构化数据（Bookmark 核心、轻量）随需提取，内容数据（Snapshot 等）按需归档，分层的另一目的是在多样部署与网络约束下优先保证"链接保存"的流畅性。第三方通道（Raindrop / S3 / WebDAV 等）均为可选项。具体存储形态与实现尚未确定，见 §5.3 与技术方案阶段。

- 外放为个人网页导航页，作为日常浏览的起点。**两种形态、同一套表现**：① 纯网页，任何地方能打开，速度较慢；② 浏览器插件（如新标签页），稳定环境下更快。**不依赖插件**也能用网页形态。核心只要基础能打开（规则/工具圈定展示范围），不优先打磨行列/小组件。是否允许完全匿名访问仍见 §4.3 / §09 #12。

- **部署与多端（产品事实）**：默认云端部署（Cloudflare Workers），其次支持 Docker 自托管。这两种部署下，多端数据走应用自己的服务，不靠 Raindrop。备份是换机/灾备兜底。选型细节见技术方案，§8.x 不是需求源。

- 当前核心聚焦 **Web 工作台 + Skill API**。插件为加速形态，不挡核心完成。移动端与 Share / URL Scheme 不作为核心，后续不排除。

## 1.2 核心理念

| 原则                 | 说明                                                                                                                                                             |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **书签为主体**          | 核心对象是"书签地址"（Bookmark），一切围绕它组织；Scene / Snapshot / Reader / 正文等是书签的组织与延伸维度，不喧宾夺主                                                                      |
| **先存下来，剩下的以后再说**   | 保存与整理无先后强制要求；保存动作优先。能连上本应用时，优先保证保存不被同步或整理打断                                                                                                                          |
| **场景化 Organize**    | 系统理解书签用途与上下文，辅助用户按"场景"（Scene）分流；用户按实际需求管理，不依赖固定信息架构                                                                                                         |
| **低成本 Rediscover**   | 收藏之后还能被找到；通过搜索、场景、最近收藏/访问、长期资料等让旧书签重新进入视野                                                                                                                       |
| **流畅操作优先**         | 书签保存流畅是核心要求：**能连上本应用即可保存**。Raindrop、对象存储等远端或第三方中断时，写入应用内临时保存，恢复后补同步；不要求在「无应用、无网络」下仍能完成保存。操作即时响应、同步不阻塞。                                                          |
| **保存与内容保全解耦**      | 保存一个链接 ≠ 保存其网页内容；Link 优先保证。Snapshot 是核心能力但**不是默认**；保存时可勾选同时截取，不勾不影响保存成功，失败也不回滚 Bookmark。保存之后仍可补做                                                                                                              |
| **渐进式归档**           | 默认只存 Link；保存时可选勾选 Snapshot（不是三选一档位）。Reader 为远景规划（见附录 B）                                                                 |
| **多渠道解耦**          | 不依赖 Raindrop / S3 / WebDAV 即可使用。多端数据走应用部署（默认 Workers，其次 Docker）。Raindrop 只作输入源和/或导出存档；备份是兜底 |
| **多入口录入**          | 核心过关：工作台保存 + Agent 保存。插件保存为加速入口，不挡核心。其他 App / 移动端 Share 为后续                                                                                    |
| **AI 能力插件化**       | Skill API 自描述，不绑定特定 AI 平台                                                                                                                                         |
| **纯个人工具**          | 不考虑多人协作，安全和隐私优先                                                                                                                                                  |
| **功能丰富，流程清晰，使用简单** | 界面与流程按使用意图组织；不把复杂度前置到保存动作上                                                                                                                                        |
| **性能优先**           | 非核心功能不增加核心路径负担，必要时可精简                                                                                                                                            |

> **核心要求**：书签保存流畅是核心要求——**能连上本应用即可准确存入书签**；第三方通道未配置或中断不阻塞保存。其余功能（整理、内容保全、导出等）均围绕"先存下来，剩下的以后再说"延伸扩展。
>
> **需求分层（本文用语）**：**核心需求**＝基础框架必须具备的能力（拆解与实现先做这一层）；**近期需求**＝核心能力完善后再扩展；**远景规划**＝产品具备一定形态后再评估。正文不用 P0/P1/P2。
>
> **术语口径**：分层**只有三层**——核心 / 近期 / **远景**。正文中出现的「远期」是**时间描述**（指某项能力中更靠后的阶段，或比远景更晚），**不单独构成第四层**，也不改变所属分层。
>
> **核心框架过关（最小集）**：工作台能保存书签 + Agent（Skill）能保存书签。
>
> **工作台核心功能（必须有）**：Inbox、列表、搜索、筛选、单条/批量改 Scene·Folder·Tag·状态、AI 建议（输入时 / 整理时 / Inbox / 未整理详情）、回收站。
>
> **有更好、非过关**：看板、标签聚合、独立整理模式、死链/域名统计等工具、浏览器插件保存、导航页插件形态（网页形态即可过关）。

## 1.3 目标用户

个人用户，有大量网页保存与长期找回需求，日常工作涉及多平台信息收集。内容保全（Snapshot）是可靠性增强，不是使用前提。

## 1.4 边界声明

**本项目是网络保存服务，不是笔记工具，也不是阅读器。**

- 不提供重型文本编辑能力

- 剪藏内容（Reader）的编辑能力属**远期规划**（见[附录 B](#附录-broadmap产品分期)），本版不实现；本版对归档内容仅支持读取、下载、重新抓取、上传替换

- 当前产品主轴是 **Capture → 场景分流 → 管理 → 搜索/浏览 → Rediscover**；Reader、阅读、高亮、笔记等"内容消费"能力是未来方向，不作为当前产品定义
- **本版不做（不挡定稿）**：移动端 App / Share Extension 优先交付；逐条点选作为导航页唯一圈选方式；Capture 时的 URL 去重；把插件当作导航页或保存的唯一形态

# 02. 核心概念

## 2.0 组织维度：Scene / Status / Folder / Tag

DogEar 的书签可通过四个**互相独立、自由组合**的维度来组织与理解。它们解决不同问题，不应互相替代：

| 维度     | 解决的问题             | 示例                     |
| ------ | ------------------ | ---------------------- |
| **Scene** | 我为什么保存 / 准备在什么情境下使用 | 工作研究、灵感收集、稍后再读、长期资料   |
| **Status** | 我目前对它做到了什么程度 / 当前状态 | 待处理（Inbox）、已确认、搁置   |
| **Folder** | 我希望它物理上/逻辑上放在哪里     | 项目A、资料库               |
| **Tag**   | 它是什么（主题/内容）         | UE5、Houdini、AI、Material |

例如：

```text
Bookmark A
Scene: 工作研究
Status: 已确认
Tag: UE5 / Material
Folder: 项目A

Bookmark B
Scene: 稍后再读
Status: 待处理
Tag: AI
```

- **Scene ≠ Folder ≠ Tag ≠ Status**：四者独立存在、自由组合，一条 Bookmark 可以同时具有某 Scene、某 Status、若干 Tag 与一个 Folder。
- 各维度均可扩展、可自定义、可停用；不是固定枚举（详见 §2.0.1 Scene 的可扩展性）。
- **Inbox / 待处理不限制其它维度**：一条待处理书签可以已有 Scene / Folder / Tag，也可以都没有；已确认也可以仍无 Scene。不强制用户先选 Scene 或先改状态才能继续用。
- 底层建模上 Scene/Status/Folder/Tag 可解耦存储。Raindrop 作为输入源时只带来 Folder（`collection`）与 Tag；**Scene / Status 只存在于 DogEar**，导出存档不写回使用场景（见 §5.2）。成员表、置信度等细部见模块文档。

### 2.0.1 Scene：场景（可扩展的组织维度）

**Scene 表示"我为什么保存它 / 我准备在什么情境下使用它"。**

- Scene 是**可扩展、可配置、可演化**的用户自定义维度，**不是固定枚举**。
- 初期提供以下**默认 Scene（初始预设 / 示例）**：**工作研究 / 灵感收集 / 稍后再读 / 长期资料**。它们不是系统最终定义，用户可以在此基础上创建新 Scene、改名、调整描述、合并、停用或删除，并重新组织自己的 Scene 体系。
- 未来不同用户可拥有完全不同的 Scene 体系（如 UE5、Houdini、AI 工具、游戏参考、产品设计、论文、购物研究、旅行计划、灵感、待验证、长期资料……），这些**都不需要修改数据库结构或代码中的固定枚举**。
- **不要将 Scene 设计为硬编码枚举**（如 `scene = "work" | "inspiration" | "later" | "reference"`），而应建模为可配置数据：

```text
Scene
├── id
├── name
├── description
├── icon / appearance（可选）
├── sort_order
├── enabled / archived
├── created_at
└── updated_at
```

- Bookmark 与 Scene 为**多对多**关联：一条书签可以同时属于多个 Scene（见 §2.0.2）。
- Scene 作为可配置数据，除上表外需能挂一个 **AERR 行为原型**（系统内部，不展示给用户，见 §2.0.3）；字段清单与成员表见模块文档。
- **注意**：当前版本只建立清晰的数据抽象与扩展方向，**不提前实现**复杂 Scene 层级、规则引擎或工作流系统。细部见 [Scene / AI 与待设计细部](../docs/module/Scene-AI与待设计细部.md)。
- 「稍后再读」是**一个 Scene（保存时的使用意图）**，而不是 Status（见 §2.0 与 §2.1.1）。用户语言中「稍后再读清单/稍后再读分区」指代归入该 Scene 的书签集合。
- 禁止用 Tag 表达「以后可能用 / 工作要用 / 值得再看」——这类意图归 Scene。
- Folder 保持稳定、通常单属；Scene 随使用情境变化，二者不互替。

### 2.0.2 Scene 归属（已确认方向）

- **一条 Bookmark 可以属于 0 个、1 个或多个 Scene。**
- **Capture 不要求选择 Scene。** 保存成功不依赖分流；未指定时进入 Inbox / 待处理即可。
- **不强制从 Inbox 转出。** 用户可以一直留在待处理，直到自己确定再改状态或补 Scene；系统可以建议，不可以把整理当成过关。
- **本版一律「建议先行」**：系统可在后台**预备**建议（高把握时生成并高亮提示），但**不自动挂载 Scene**，须用户点击确认后才写入；低把握不生成建议，留在 Inbox。自动分流不作为本版能力（AI 边界见 §6.1）。
- Scene 可事后追加、移除、迁移（例如研究结束后从「工作研究」转到「长期资料」，或两头都留）。改的是情境关系，不拆 Folder / Tag。
- UI 允许多属，但不要做成「一次勾选十个场景」。默认强调当前打开的那个 Scene，其它用弱展示（如「同时用于长期资料」）。
- **第一版不做 Primary Scene 字段。** 呈现上下文 = 用户当前所在的 Scene 视图。是否引入主场景见模块文档。

### 2.0.3 AERR 行为原型（系统层，不展示给用户）

AERR 是系统理解 Scene 的内部类型，不是用户分类：

| 原型 | 含义 | 默认挂到 |
| --- | --- | --- |
| **Action** | 近期要拿它办事 | 工作研究 |
| **Explore** | 浏览、发散、找灵感 | 灵感收集 |
| **Read** | 准备消费掉 | 稍后再读 |
| **Reference** | 以后反复查 | 长期资料 |

- **不把 Action / Explore / Read / Reference 作为用户必选项。**
- 用户新建 Scene 时，系统给一个默认原型（可改）；用户不必理解这四个词。
- **工作台只有一套。** 不同 Scene 改变的是默认排序、信息密度和主按钮，不是另一套页面。第一版可先共用列表，只换主操作文案。
- 同一书签出现在不同 Scene 时，跟随**当前视图**的原型呈现（在「工作研究」里偏行动，在「长期资料」里偏检索）。
- 「纯备份」并入 Reference，不单列第五种原型。

### 2.0.4 Scene 与 AI 的关系（已确认方向）

AI 服务于 Scene，不是把产品做成聊天式阅读器。

| 分层 | AI 做什么 | 不做什么 |
| --- | --- | --- |
| **核心需求** | 保存后异步理解页面；建议 1 个 Scene 和很少的 Tag/Folder；用户有一句话意图时按意图分流；建议默认可撤销 | 低把握乱贴场景；不经确认改结构；删除数据 |
| **近期需求** | 记住「这类东西你常放哪」（组织习惯）；闲置的工作研究可建议迁到长期资料；相似 Scene 过多可提示合并 | 自动迁移、自动合并、自动生成一套分类哲学 |

两条记忆分开：

- **书签记忆（核心，浅做）**：这是什么（标题、类型、短理解）
- **组织记忆（近期）**：你通常怎么放

**建议出现位置（核心）**：输入时（页面 / 插件 / Skill）、整理时、Inbox 界面内、未整理书签的详情页。不强迫进入整理模式才能看到建议。

详细置信度、迁移阈值、成员表字段不在本 PRD 展开，见 [Scene / AI 与待设计细部](../docs/module/Scene-AI与待设计细部.md)。

## 2.1 Bookmark：长期引用对象

Bookmark 是系统中长期存在的网页引用对象，不因其内容归档状态而变化。

```
Bookmark
├── 基础属性（随链接保存、一般不变的信息，字段明细见技术总纲 §5.7）
│   ├── 标识：应用 ID（本应用自维护；本地未推送真源前为 `tmp_` 前缀临时 ID，推送成功后回填）＋ `raindropId`（Raindrop 侧 `_id`，仅启用该通道时存在，同步时传出用于数据匹配，见 §5.2）
│   ├── URL（链接地址，必填）
│   ├── Metadata（系统保存时自动抓取的网页描述字段，是基础属性子集，可被用户修正）
│   │   ├── Raindrop 同构（有官方对应，可同步）：Title / 描述（Raindrop 字段 excerpt）/ Cover / Type 等
│   │   └── 本地扩展抓取（Raindrop 无对应，仅存本地、不同步）：Author / Favicon / Published At 等
│   ├── 用户维护字段（可随导出写入 Raindrop 存档）：Tags / Folder（Raindrop 字段 collection）/ Notes（Raindrop 字段 note）/ Important（收藏标星，见 2.1.2）/ Highlights / Reminder（后二者无独立产品入口，随通道保留）
│   └── Raindrop 其他字段：Broken / File / CreatorRef / Domain（Raindrop 派生，只读）
├── Scenes[]（可多属，见 §2.0.2；Capture 可不填）
├── Source（录入来源：page / agent / extension；app 为后续）
├── Status（Inbox 待处理 / 已确认 / 搁置，仅应用内；导出 Raindrop 存档不携带 Inbox 语义，见 2.1.1）
├── 导航展示（由规则/工具圈定，非逐条必选，见 §4.3）
├── 访问记录（核心需求：记录打开行为，交互后定，见 §4.5）
├── Created At / Updated At
└── Archives[]（关联的内容归档，见 2.2）
```

**Metadata 界定**：本产品中 Metadata 特指**系统在保存时自动抓取的网页描述字段**（网页标题、描述、封面、类型、作者、站点图标、发布时间等），是基础属性中"自动产生"的子集；Tags / Folder / Notes 等由用户维护的字段不属于 Metadata。抓取结果允许用户修正，修正后以用户修正值为准。其内部按 Raindrop 官方 API 是否存在对应字段分为两组：

- **Raindrop 同构**：Raindrop 官方 API 存在对应字段，可随基础属性同步至 Raindrop（如 `title`、`excerpt`、`cover`、`type`）

- **本地扩展抓取**：Raindrop 官方 API 无对应字段，仅存于本地数据库、不参与 Raindrop 同步（如 `author`、`favicon`、`publishedAt`）

> 注意区分：本产品中的 **Metadata** 专指上述"自动抓取的网页描述字段"，与中文"元数据"（泛指描述数据的数据，如数据库中的 Bookmark / Job / Record 结构化记录）含义不同——后者在文档中单独表述（见 §5.1、§8.x.3），不共用同一概念。

逐字段的 Raindrop 对应关系、数据级别与存储位置见[技术总纲 §5.7 字段与 Raindrop 映射总表](../docs/DogEar_折耳书签_技术总纲_v1.0_DeepSeek.md)（原附录 C 已迁移承接）。

**关键约束**：创建 Bookmark 时不要求一定完成网页内容抓取。一个只有 URL 和 Metadata 的 Bookmark 是完整且有效的。

### 2.1.1 状态体系

书签状态围绕**「对这个书签的处理程度」**设计，不设持续性的「在读」状态（与「书签为主体、非稍后读工具」的理念一致）。产品概念上聚焦 **Inbox / 待处理**——表达的是「我还没有决定这个书签下一步怎么处理」，而非「用户还没有阅读这篇文章」。

**命名约束（v1.0.4）**：状态「搁置」与内容层 **Archive / Snapshot（网页保全副本）** 不是同一件事。正文与 UI **禁止**再用「已归档」指代 Status，以免与内容保全混淆。

| 状态（对外） | 底层字段 | 产品概念 | 含义 | 说明 |
| --- | --- | --- | --- | --- |
| **待处理** | `unread` | Inbox / 待处理队列 | 尚未决定去向 | 新保存书签的默认状态，是随时录入的入口队列 |
| **已确认** | `saved` | 已确认值得保留 | 整理后确认保留 | 确认有长期保留价值的书签 |
| **搁置** | `archived` | 低价值暂留 | 暂不处理、暂不删除 | 价值较低、暂无删除意愿，可随时删除或恢复为待处理/已确认 |

- 新录入默认进入「待处理」（Inbox）；用户**可以**在确定后转为「已确认」或「搁置」，**不是必须**
- 待处理可长期停留，不因未分流、未选 Scene、未整理而失效或被系统改写
- 待处理与已确认都不限制 Scene / Folder / Tag 是否已填
- 搁置不等于删除，搁置的书签仍可检索与恢复
- 搁置也不等于已生成 Snapshot：一条「已确认」的书签可以没有 Snapshot；一条「搁置」的书签也可以已有 Snapshot
- 删除走应用内软删除（回收站），与「搁置」不是同一件事；导出存档默认不含回收站条目（见 §4.2.12）
- 状态只存在于应用内；导出 Raindrop 存档不把 Inbox / 已确认 / 搁置写成使用场景（见 §5.2）
- **底层字段保留 `unread` / `saved` / `archived` 以兼容同步与既有数据**；产品 UI 与语言统一用上表对外名称，避免把 DogEar 塑造成阅读/稍后读工具

> 状态 ≠ Scene：「稍后再读」是 Scene（保存意图），不属于本状态体系；一条书签可以是「稍后再读 Scene + 待处理状态」，二者互不冲突。

### 2.1.2 收藏标星（Important）

- **收藏**（收藏标星，`important`）是与三态独立的功能属性：对某个书签"打上标星"，标记为个人收藏

- Raindrop 字段名 `important`，本产品沿用；交互形态为"标星"（非红心）

- 收藏标星与状态流转互不干扰：待处理 / 已确认 / 搁置的书签均可标星

## 2.2 Archive：可异步产生的内容副本

Archive 是与 Bookmark 解耦的、可异步产生的内容副本。同一个 Bookmark 可以对应多个 Archive，也可以没有任何 Archive。

**Archive 是"内容保存 / 长期保全"这一层**。当前结构定位：

```text
Bookmark
├── Link（基础：URL + Metadata）
└── Archive（内容保存 / 长期保全）
    ├── Snapshot（网页原貌长效保全，当前）
    └── Reader（清洗阅读版，远期规划）
```

| 类型           | 目标       | 内容                 | 触发方式        | 存储与同步                               | 阶段   |
| ------------ | -------- | ------------------ | ----------- | ----------------------------------- | ---- |
| **Link**     | 快速保存     | URL + Metadata     | 默认，任何录入方式   | 应用内保存；可选导出至 Raindrop 存档         | 当前   |
| **Snapshot** | 网页内容长效保全 | 完整 HTML + CSS + 资源 | 保存时可选勾选（默认不勾）；保存后仍可补做 | 内容存储层（形态见技术方案），不进 Raindrop | 核心能力、非默认 |
| **Reader**   | 清洗阅读版    | 清洗后的正文 + 必要资源（图片等） | 用户主动 / 策略自动 | 内容存储层（同 Snapshot），不同步               | 远期规划 |

**Snapshot 的核心价值**：当用户希望**长期保存**某个网页时，将网页内容进行**本地化、完整化保存**，以降低原网页失效、修改或删除带来的风险。Snapshot 的定位是 **Preservation / Archive（内容保全）**，而非 **Reader / Reading Experience（阅读体验）**——它不承担 DogEar 的核心阅读入口职责。

**核心原则**：

- Bookmark 永久存在，Archive 可以异步产生、失败、重试和重复生成

- 某次 Archive Job 失败不代表 Bookmark 失败

- Snapshot 是当前可用的内容保全形态（"保存网页"）；Reader 是"保存清洗后内容"，为远期规划（见[附录 B](#附录-broadmap产品分期)），二者定位不同、互相不替代

- 用户视角的属性分层（正式表述，见 §09 待决策 #7）：书签属性按生成时机与稳定性分为三层，优先级递减：

  - **基础属性**：随链接保存、以 Raindrop 官方 API 为字段基准的网页属性（Bookmark 结构见 §2.1），是保存书签时即具备、一般不变的信息。字段清单以 Raindrop 官方对象字段为基准校准（如描述字段官方名为 `excerpt`、文件夹官方名为 `collection`），按"是否可同步至 Raindrop"分两组：

    - **① Raindrop 同构（可作输入读入 / 导出存档写出）**：Raindrop 官方 API 存在对应字段。✅ 当前产品启用：`_id`（Raindrop 侧 ID；本应用另自维护应用 ID，两者并存见 §2.1）、`link`（URL）、`title`、`excerpt`、`cover`、`collection`、`tags`、`note`、`created` / `lastUpdate`、`important`（收藏标星，见 §2.1.2）、`type`、`broken`、`domain`（Raindrop 派生、只读）。**不把** `_status`、删除标签、Scene 写入 Raindrop 存档。
    - ⚠️ **`highlights`**：Raindrop 官方字段，映射表保留以便输入/导出时不丢数据（见技术总纲 §5.7.1）；**当前版本无高亮产品入口**。若从 Raindrop 读入则只读保存，工作台不提供创建/编辑高亮。
    - ⚠️ **本版无独立产品入口、仅同步保留的字段**：`reminder`（提醒）、`file`（附件）、`creatorRef`（创建者引用）。排序文案中的「优先级」本版不单列为书签属性（收藏标星已覆盖「我更在意」）。说明见技术总纲 §5.7.5 与模块文档。

    - **② 本地扩展抓取（Raindrop 无对应，不同步）**：系统保存时自动抓取、但 Raindrop 官方 API 无对应字段的网页描述信息，仅存于本地数据库：`author`（作者）、`favicon`（站点图标）、`publishedAt`（页面发布时间）等（属 Metadata 的子集，见 §2.1）

    - 🚫 **排除**：`cache`（Raindrop PRO 会员专属的永久副本，非会员不可用）

    - ⚠️ **观察**：Raindrop 其他未启用字段（如 `media`、`html`、`data` 等），不依赖其存在，后续按需评估

  - **内容信息**：链接背后需要固化的内容（Reader 阅读版正文 / Snapshot 网页快照等 Archive 内容），可随时间更新或被用户修改，优先级低于基础属性，内容不入 Raindrop、存于内容存储层（具体存储形态与选型待技术方案阶段确定，见 §5.3；原"高级信息"表述）

  - **扩展属性**：用户自定义属性，本版仅声明存在，字段清单与交互待后续细化

  > 两组字段的逐项 Raindrop 对应关系、数据级别与存储位置见[技术总纲 §5.7 字段与 Raindrop 映射总表](../docs/DogEar_折耳书签_技术总纲_v1.0_DeepSeek.md)。

## 2.3 Archive Job：归档任务

Archive Job 是独立的异步任务抽象，负责将网页内容转化为 Archive。

```
ArchiveJob
├── id
├── bookmark_id（关联 Bookmark）
├── type（metadata / snapshot；reader 为远期规划预留）
├── source（agent / browser / server / manual）
├── status（pending / processing / completed / failed / cancelled）
├── created_at / started_at / completed_at
├── error（失败原因分类）
└── result（归档结果引用）
```

**type 说明**：

- `metadata`：抓取网页描述字段（Metadata，见 §2.1）的异步任务。产出写入 Bookmark 基础属性——Raindrop 同构字段（Title / Excerpt / Cover 等）可同步至 Raindrop，本地扩展抓取字段（Author / Favicon / Published At 等）仅存本地；不生成内容 Archive、不写入内容存储层。抓取失败不影响 Bookmark 有效性与同步（可后续重试）

- `snapshot`：生成网页快照（Snapshot Archive），内容写入内容存储层，不入 Raindrop

- `reader`：清洗阅读版归档，为远期规划预留

**多来源策略**：

- **Server Fetch**：服务器自动抓取，适合批量和 Agent 保存后的后台处理；**默认部署（Workers）下仅承担 Metadata 抓取**，整页 Snapshot 需浏览器端补做或改用 Docker 轨（运行环境预算所限，见技术总纲 §6.4）

- **Browser Fetch**：利用用户已渲染的页面 DOM，成功率最高，适配动态渲染页面及需登录访问的内容（当前用于 Snapshot / Metadata；手动选择正文区域属远期 Reader，见附录 B）

- **Agent Fetch**：Agent 创建 Bookmark 后触发，或仅创建 Link 等待后续处理

- **Manual**：用户手动触发 Snapshot（手动选择正文区域属远期规划）

**核心原则**：服务器负责自动化，浏览器负责高成功率和高保真度。

**抓取分级（已确认方向）**：不同归档能力对性能与运行环境的消耗差异大，需按**任务重量、触发源、设备与网络条件**三个维度分级规划——先获取什么、什么时机获取、满足什么条件才获取，逐项判断而非一刀切。分级与调度细则见技术总纲 §6.4，本文只定方向。

## 2.4 内容提取策略（方向性）

当前版本的页面提取主要用于：**补 Metadata、帮助 AI 理解、按需生成 Snapshot**。不把 Reader、手动选正文作为产品入口。

方向：多来源、可降级，不依赖单一解析器；某次提取失败不影响 Bookmark 有效性。完整的 Reader 降级链（含站点规则、手动选正文）见[附录 B](#附录-broadmap产品分期)，原文细部亦收入模块文档以免丢失。

若用户明确要求完整保存网页：在保存成功之后触发 Snapshot 流程（不是 Capture 时选档）。

# 03. 用户工作流

## 3.0 首次使用与数据管理

首次使用**不引导登录 Raindrop**。只引导做一次**数据管理选择**（可跳过、可稍后在设置中改）：

- 可以不接任何第三方，立刻开始保存与整理
- 数据管理可选范围：**Raindrop**、**S3**、**WebDAV** 等，均为选项，可跳过、可多选
- Raindrop 若选用，只扮演两种角色（可只开一个）：**输入源**（把已有库引进来）和/或 **导出方向**（把 Link 级记录存档出去，不携带 Scene 等使用场景）

**作为输入源时**（仅当用户选用了该输入）：首次导入可选「进 Inbox」或「保持原路径」，可走导入梳理页（复用整理模式，可跳过）。**首次梳理完成之后**，从该输入源新进来的零散记录一律进入 Inbox。DogEar 自己保存的新书签默认也进 Inbox。

**作为导出方向时**：导出为存档，不是双向同步；不导出 DogEar 使用场景。

通道怎么接、字段怎么映射、任务怎么跑，本文不规定。现行技术方案待重建（迁出细部见归档稿）。

## 3.1 录入工作流（Capture）

用户在这个环节只负责一件事：**"这个链接我先存下来。"**

- 不要求用户在收藏瞬间完成：文件夹选择、标签填写、Scene 选择、阅读、摘要、内容整理

- 默认 Capture 结果为 **Link 级**（URL + Metadata）。Snapshot 是核心能力但不是默认：保存时**可勾选**「同时截取快照」，不勾选也能保存成功；勾选了但截取失败，Bookmark 仍然成立。保存成功之后仍可再补 Snapshot。不是「存链接 / 存快照 / 存阅读版」三选一。

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  页面录入    │   │  Agent 录入  │   │ 浏览器插件   │
│  (Web 表单)  │   │  (Skill API) │   │  (Extension) │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │                 │                 │
       └─────────────────┴─────────────────┘
              （其他 App / Share：后续，非本版优先）
                         │
                         ▼
                  ┌─────────────┐
                  │  Bookmark   │
                  │   Created   │
                  │  (Link 级)   │
                  │  默认入 Inbox │
                  └──────┬──────┘
                         │
              ┌──────────┴──────────┐
              │  理解 / 元数据获取   │
              │ （异步，不阻塞保存）  │
              └──────────┬──────────┘
                         │
              ┌──────────┴──────────┐
              │  Scene 分流（可选）   │
              │（系统建议 / 用户确认）│
              └──────────┬──────────┘
                         │
                         ▼
              后续管理 / 搜索 / 浏览
```

**理解 / 元数据获取**（异步、不阻塞保存）：系统根据 URL、页面标题、页面内容、用户历史行为、已有标签/文件夹、收藏上下文与用户主动描述等，理解书签的用途与上下文，辅助判断 Scene / Folder / Tag / 标题 / 描述。AI 可推荐；结构类字段（Scene / Folder / Tag）默认不自动写入（AI 安全边界见 §6.1）。

**分流**（Scene 分流为"可选项"，非强制步骤）：系统可建议 Scene / Folder / Tag，用户可接受、修改或跳过——**保存动作本身永不因分流而受阻**。

**浏览器插件录入**：

- 利用用户已正常访问和渲染的页面

- 可直接获取当前 DOM 进行内容提取

- 插件保存默认只创建 Link；可勾选同时截取 Snapshot（可选，非档位三选一）。不勾或截取失败都不妨碍保存。保存后仍可补做

- 不为当前版本提供 Reader 保存档位

- **手动选择正文区域**：属 **远期规划**（见[附录 B](#附录-broadmap产品分期)），服务于未来 Reader，不进入当前插件主路径

- 本版 **不定义 URL 去重产品规则**（先前「识别重复并合并/追加」的表述收回，待日后单独立项）

## 3.2 整理工作流

### 3.2.1 工作台整理

- **Inbox / 待处理队列**：展示待处理（`unread`，见 §2.1.1）的书签；用户可在这里停留、浏览、补 Scene，**不强制**先做保留/删除或改状态

- **两阶段分拣**（可选加速，不是必经关卡）：

  - 阶段一：是否保留（快速决策）

  - 阶段二：如何分流（确认价值 → 转为「已确认」或「搁置」；系统按理解结果建议 Scene / Folder / Tag，用户确认或修改）

- **导入梳理页**：选用 Raindrop 等输入源并首次导入后，可用同一套分拣/批量/AI 建议能力快速过一遍（见 §3.0）；可跳过

- **多视图切换**：网格 / 列表 / 看板

- **按 Scene 浏览**：工作台支持以 Scene 为维度筛选与浏览（默认 Scene + 用户自定义 Scene，见 §2.0.1/§4.2.3）

- **Archive 状态展示**：Bookmark 卡片展示各归档类型的完成状态（如 Link✓ / Snapshot✗）；Reader 归档类型属远期规划，状态位预留

### 3.2.2 内联编辑

悬浮卡片时浮现操作区：

- Scene 切换（默认 Scene 或用户自定义 Scene）

- 文件夹移动

- 标签增删

- 状态切换

- Archive 操作（触发 Snapshot 抓取、查看已保全内容；触发 Reader 属远期规划）

### 3.2.3 批量操作

多选后出现批量工具栏：

- 批量设置 Scene（如统一归入某 Scene）

- 移动到文件夹

- 添加标签

- AI 批量整理（AI 回填信息，预览后确认生效）

- 触发批量 Snapshot 归档（批量 Reader 属远期规划，见[附录 B](#附录-broadmap产品分期)）

- 标记已确认 / 搁置 / 删除

## 3.3 浏览与导航工作流

### 3.3.1 导航页（基础框架）

导航页是 **Bookmark 的访问 / 展示 / 重新发现层**，不是另一个 Bookmark 管理器：它展示用户主动选择 / 系统辅助推荐的一组"值得被再次访问"的书签，作为个人网页浏览的起点。**网页形态与插件形态表现一致**；核心过关只需网页能打开。第一版默认随工作台登录（详设见 §4.3）。

基础框架包含：

- **固定区域**（顺序与是否展示待定）：

  - 时间/搜索区

  - 页面标签区

  - 小组件区（可含 Rediscover 卡片，如最近收藏 / 最近访问 / 长期未访问 / 某 Scene 随机书签，见 §4.3/§4.5）

  - 文件夹图标区

  - 书签图标区

  - Docker 栏

- **核心交互**：

  - 书签以图标+名称展示，点击打开

  - 文件夹以聚合图标展示，点击展开浮层

  - 搜索框支持模糊匹配标题与域名

  - 长按/右键菜单

**详细设计标为待定**，后续专题讨论。

### 3.3.2 归档内容浏览（Snapshot 保全内容查看）

- Snapshot 内容：以原始网页形态展示（或近似还原）——定位是"查看已保全的网页"，而非产品核心阅读入口

- Reader 内容（**远期规划**，见[附录 B](#附录-broadmap产品分期)）：以清爽阅读模式展示，支持基本导航

- 内容操作：下载、重新抓取、上传替换（Reader 编辑能力受限，属远期规划）

- **追加 Archive**：对已有 Bookmark 补充 Snapshot，不创建新 Bookmark（补充 Reader 属远期规划）

- **单条内容信息导出**：对单个网页的内容信息（Snapshot 快照 / Reader 阅读版等 Archive 内容）按需导出，先选择要打包的内容，再选择导出格式（HTML / PDF / Markdown），见 §4.6.3

# 04. 功能模块

## 4.1 录入层（Capture）

| 录入方式 | 是否核心过关 | Capture 默认 | 可选（保存时勾选） | 特点 |
| --- | --- | --- | --- | --- |
| 页面快速保存（工作台） | **是** | Link | 同时截取 Snapshot | 输入 URL；不勾选也能保存成功 |
| Agent (Skill API) | **是** | Link | 可选 snapshot 开关，默认关 | 仅 URL 即可创建；没说就不截 |
| 浏览器插件 | 否（加速入口） | Link | 同时截取 Snapshot | 可用当前 DOM 提高保真度。不挡核心完成 |
| 其他 App | 否 | Link | 后续 | 非核心（Share / URL Scheme 等） |

**Archive 策略**：

- 默认：只存 Link。Snapshot 是核心能力、非默认
- 保存时可勾选同时截取；失败不回滚 Bookmark
- 保存之后仍可补做 Snapshot
- Agent 保存后自动截取：仅当用户显式打开该选项，默认关
- Reader 为远景规划

## 4.2 工作台

工作台是核心操作界面，承载书签从「收集 → 理解/分流 → 管理 → 搜索/浏览 → 重新发现」的产品主轴，并集中管理同步、备份、AI 接入等系统能力。

**一套工作台，不是按 Scene 拆四套产品。** 左侧 Scene 是入口和当前上下文；主区结构不变，仅按该 Scene 所挂 AERR 原型调整默认排序、密度和主操作（见 §2.0.3）。核心过关先做列表。

**核心必须有**：Inbox、列表、搜索、筛选、单条/批量改 Scene·Folder·Tag·状态、AI 建议四个落点、回收站。

**有更好、非过关**：看板、标签聚合、独立整理模式、死链/域名统计等右侧工具。

### 4.2.1 整体布局

- 左侧：分类导航（Scene 分区、状态分区、文件夹树、标签云）

- 顶部：快速搜索（⌘K）、AI 整理入口、同步状态、设置

- 中部：主内容区，支持多视图切换

- 右侧：可折叠工具面板（默认收起）

- 底部：状态栏（同步状态、Inbox 待处理数量）/ 批量操作栏

### 4.2.2 分类导航

- **Scene 分区**：默认 Scene + 用户自定义 Scene（见 §2.0.1），各分区显示数量；Scene 可管理（新建/改名/合并/停用/删除）

- **状态分区**：待处理（Inbox）、已确认、搁置，各分区显示数量

- **文件夹分区**：树形结构，支持展开/折叠

- **标签分区**：点选过滤，支持快速定位与取消筛选

### 4.2.3 浏览与筛选

- **搜索**：关键词搜索标题/URL/标签/备注

- **筛选**：按来源（AI / 扩展 / Raindrop）、按 Scene、按文件夹、按标签、按状态、按时间、按是否在导航页展示

- **排序**：时间 / 标题 / 收藏标星等；本版不单列「优先级」属性（见技术总纲 §5.7.5）

- **视图**：核心过关为列表（可含卡片密度）。标签聚合 / 看板为非过关。空状态提供引导提示

### 4.2.4 状态管理

书签状态流转：**待处理（Inbox）→ 已确认 / 搁置**（与 Scene 解耦，见 §2.1.1）

- 看板视图下支持拖拽跨列迁移状态（看板为非过关）

- 每条记录携带：来源、Scene、文件夹、标签、加入时间、Archive 状态

### 4.2.5 详情与操作

- **详情面板**：点击书签打开，展示完整信息、原链接、Archive 状态、操作入口

- **单条操作**：设置 Scene、标记已确认/搁置、移入回收站、增删标签、触发 Snapshot、导出内容信息

- **批量操作**：多选后批量设置 Scene、批量标记已确认/搁置、批量加标签、批量移入回收站

- **操作反馈**：轻量级消息提示（Toast），删除等操作支持撤销

### 4.2.6 整理模式（可选 · 两阶段分拣）

整理模式与导入梳理页是**可选加速工具**，不是 Inbox 清零义务。用户可以永远不进整理模式，只在待处理里用。

**阶段一 · 分拣（是否保留）**：

- 目标：快速判断保留 / 删除 / 待定

- 少量（<10 条）：逐条操作

- 大量（>10 条）：支持多选 + 批量标记

- 实时统计：保留 N / 删除 N / 待定 N / 待处理 N

**阶段二 · 细分拣（如何分流）**：

- 仅展示阶段一标记为"保留"的条目

- 确认价值 → 转为「已确认」或「搁置」

- 展示系统按理解结果建议的 Scene / 文件夹 / 标签（AI 建议见 §4.2.7）

- 用户可逐条采纳/修改，或批量采纳

### 4.2.7 AI 整理建议（核心需求）

- 系统给出建议：优先 1 个 Scene，其次很少的文件夹 / 标签，可附一句说明
- **出现位置**：输入时（页面保存 / 插件 / Skill）、整理时、Inbox 界面内、未整理书签的详情页
- 建议状态：待处理 → 接受 / 稍后处理 / 忽略
- 采纳后即时生效，支持撤销
- 不强制进入整理模式才能看到建议
- **默认不自动执行。** 低把握不写 Scene。未来若提供自动分流，需显式开启且可追溯、可批量撤销（见 §6.1）
- Agent 保存时：用户带了意图（如「以后做材质用」）则按意图建议；未带则按内容理解建议，规则同上

### 4.2.7a AI 组织记忆与迁移（近期需求，当前不作为能力承诺）

- 记住用户把某类内容放到哪个 Scene / Folder 的习惯
- 对长期未访问的「工作研究」等，可建议迁到「长期资料」——只建议，不自动改
- 自然语言「上次那个 xx」检索为近期需求；核心需求以标题 / 地址 / 标签 / 备注 / Scene 过滤为准
- **访问记录（核心需求）**：打开原链接（及日后打开 Snapshot）应留下访问记录，供 Rediscover「最近访问 / 长期未访问」使用；字段、去噪与界面后定，见模块文档

### 4.2.8 右侧工具面板

| Tab     | 内容                         |
| ------- | -------------------------- |
| **工具**  | 死链检测、标签整理、域名统计（**非过关**；「重复保存」本版不作为产品规则） |
| **待处理** | Inbox 待处理紧凑列表，底部「进入整理模式」入口  |
| **统计**  | 总保存数、各状态数量、各 Scene 数量、新增趋势、Archive 分布 |

### 4.2.9 数据通道与 Raindrop

- **本地保存即时生效**；第三方通道未配置或中断不阻塞使用
- 数据管理选项与 Raindrop / S3 / WebDAV 等并列，范围见 §3.0；做法待技术方案重建

### 4.2.10 备份与恢复

备份是换机 / 灾备**兜底**，不是日常多端同步手段（多端见 §8.2）。

- **三档备份**：轻量（HTML/CSV/Markdown）、中等（含配置）、完整（ZIP 快照）

- **备份目标**：与数据管理选项一致，支持 WebDAV、S3 等，可独立启用；怎么接待技术方案重建

- **备份历史**：展示时间、目标、结果、体积

### 4.2.11 Agent 接入

- **能力开关**：查询 / 保存 / 编辑 / 批量整理 / 删除，按需启用

- **速率限制**：读、写、批量操作分别设上限

- **用量观测**：今日请求量、写入量、被拦截次数

- **凭证与设置（方向）**：Raindrop Token、Skill Token、备份目标、能力开关集中在设置里；不配置 Raindrop 时产品仍可保存与整理。设置页交互见既有原型与模块文档，本文不展开。

### 4.2.12 日志与回收站

- **操作日志**：同步、整理、新增、编辑、删除、AI 调用、备份等行为全留痕

- **日志保留**：有限保留（默认 5000 条 / 30 天，可配置），支持清理/导出/循环覆盖

- **回收站**：软删除机制，删除书签进入回收站，保留天数可配置（默认 7 天），支持恢复与清空

- **删除与导出**：软删除留在应用内回收站。导出到 Raindrop 的存档**默认不含回收站条目**。不再把「删除标签双向推送」当作核心数据模型；若导出存档需要反映删除，细则见模块文档

## 4.3 导航页（访问 / 展示 / 重新发现层）

### 4.3.1 定位与形态

导航页是 **Bookmark 的访问 / 展示 / 重新发现层，不是另一个 Bookmark 管理器**。**两种形态、同一套表现，不依赖插件**：

| 形态 | 特点 |
| --- | --- |
| **纯网页** | 任何地方能打开，速度较慢。核心过关只需这一种 |
| **浏览器插件**（如新标签页） | 稳定环境下更快。与网页表现一致，技术路径不同。不挡核心完成 |

核心只要基础能打开（规则圈选 + 图标可点）；行列、小组件、Docker 打磨不优先。它不承担收藏管理（Scene/Folder/Tag/Status/Archive 在 §4.2 完成）。

- **工作台必须登录**。导航页是访问层，不等于默认公开全库。
- **第一版默认**：导航页与工作台使用同一登录会话；匿名访问不是默认能力。
- **展示范围**：由工作台用**规则或工具**圈定「是否在导航页展示」，不是传统一条一条勾选。方向与 `AGENTS.md` 一致：**全部 / 按规则（或） / 自定义搜索勾选 / 隐藏**。规则结果持久化为展示集合；关闭导航页不丢页面标签与 Docker 配置。
- Inbox / 待处理、被规则排除的条目、私密文件夹默认不出现（除非规则明确纳入）。
- 若未来提供「无需登录的公开导航」，仅针对上述已圈定条目，且只含标题、图标、URL，不含笔记、Inbox、私密内容。可见范围细则见 §09 #12。

- 形态见上表：网页与插件表现一致；详细视觉打磨待定，不阻塞需求定稿

- **长期演化方向**（架构预留，当前版本不强制拆分实体）：`Bookmark → Navigation Item → Navigation Page`，避免在 Bookmark 实体上堆积大量 UI 展示属性；是否拆独立实体、拆到什么程度保留为"待设计"（见 §09）

### 4.3.2 已确认的基础要素

- 图标+名称的书签展示方式

- 文件夹聚合图标+展开浮层

- 顶部搜索框

- 固定区域规划（时间/搜索 → 标签 → 小组件 → 文件夹 → 书签 → Docker）

- 网格布局

- 显示控制：工作台侧用规则/工具决定"是否在导航页展示"，导航页侧决定展示样式；未来在此基础上扩展为"值得被再次访问"的推荐与自定义集合（见 §4.3.1 长期演化方向）

- Rediscover 卡片：小组件区可展示最近收藏 / 最近访问 / 长期未访问 / 某 Scene 随机书签等（见 §4.5），让导航页同时承担"重新发现"入口

- 隐私：私密内容默认隐藏，查看需解锁

- Docker 栏：底部常驻快捷栏

### 4.3.3 待定细节

- 具体行列数与响应式规则

- 小组件的具体类型与尺寸

- 拖拽排序的完整交互

- 页面标签的详细设计

- 跨页/跨区拖拽

- 导航页无需登录时的可见范围 / 内容选择规则（哪些内容允许匿名访问）

规则圈选的具体算子、预览与冲突（例如「全部」与「隐藏某文件夹」同时存在）见模块文档，本文只定「规则/工具，非逐条」。

## 4.4 Skill API

### 4.4.1 自描述机制

AI 平台绑定时只需提供服务地址（Base URL）+ 访问令牌（Token）。AI 通过访问 `/.well-known/capabilities` 自动获取能力列表。

### 4.4.2 Skill 清单

| Skill              | 描述   | 输入                                         | 说明                                            |
| ------------------ | ---- | ------------------------------------------ | --------------------------------------------- |
| `save_bookmark`    | 保存链接 | url（必填）、note（可选）、intent（可选）、snapshot（可选，默认否） | 创建 Link 级 Bookmark；可建议 Scene / Folder / Tag，**默认不自动写入结构**。`snapshot` 为保存时勾选的等价开关，默认关；截取失败不回滚 Bookmark。保存后补做仍用 `trigger_archive` |
| `search_bookmarks` | 搜索书签 | query、filters（可选）                          | 核心：标题/URL/标签/备注与条件筛选（Scene/状态/文件夹/标签/时间）。自然语言检索为近期需求 |
| `update_bookmark`  | 修改书签 | id、修改字段                                    | Scene/文件夹/标签/备注/状态                             |
| `list_bookmarks`   | 列出书签 | Scene、状态、文件夹、标签、limit                      | 支持筛选和分页                                       |
| `get_stats`        | 获取统计 | 无                                          | 保存总数、各 Scene/分类数量等                              |
| `trigger_archive`  | 触发归档 | bookmark\_id、type（snapshot；reader 为远期规划预留） | 为已有 Bookmark 创建 Archive Job                   |
| `suggest_scene`    | 建议分流 | bookmark\_id（或批量 id）                         | 系统理解书签后建议 Scene/Folder/Tag，需用户确认后生效（AI 边界见 §6.1） |

### 4.4.3 AI 记忆

**核心需求（当前）**：对单条书签做浅理解（标题、类型、短描述），用于建议 Scene，不形成必须维护的记忆产品。建议出现在输入、整理、Inbox、未整理详情（见 §4.2.7）。

**近期需求（方向）**：

- 组织习惯记忆（这类东西你常放哪）
- 可预览、修改、重置
- 隐私内容可标记不进入记忆
- 自然语言关联检索

近期需求细节写入 [Scene / AI 与待设计细部](../docs/module/Scene-AI与待设计细部.md)，不在本版展开能力清单。

## 4.5 搜索与 Rediscover

- **搜索范围**：本地标题/URL/标签/备注，支持过滤（Scene/文件夹/标签/状态/时间）

- **实现方向**：本地搜索为主，必要时可调外部 API；不做全文正文索引

- **排序**：相关度 + 时间综合。核心需求不承诺自然语言 query；自然语言与 AI 记忆联动为近期需求（见 §4.2.7a）

- **交互**：工作台 ⌘K 命令面板，导航页顶部下拉列表

- **访问记录（核心需求）**：记录用户打开书签的行为，作为「最近访问 / 长期未访问」的数据前提。记什么字段、如何展示后定。

**Rediscover（重新发现）**：搜索之外，"让过去收藏的内容重新进入视野"是一级产品目标（见 §1.1）。访问记录属核心需求（先记下来）；卡片与回顾形态按近期需求评估（见[附录 B](#附录-broadmap产品分期)）：

- 最近收藏 / 最近访问

- 长期未访问（"旧书签提醒"）

- 某 Scene 下的随机书签 / 相关 Bookmark / 相似 Bookmark

- 历史收藏回顾（如 N 年前今天保存了什么）

- AI 推荐重新查看（基于内容相关性与用户场景）

- 导航页小组件展示（见 §4.3.2 Rediscover 卡片）

| **轻** | 通用迁移 | Link 级数据（HTML/CSV/Markdown）                            | 第三方可读，不含个性化配置 |
| **中** | 配置还原 | Link + 个性化配置（含 Reader 属远期规划，见[附录 B](#附录-broadmap产品分期)） | 导入可还原核心体验     |
| **重** | 快照灾备 | 完整本地库 + Snapshot + 配置                                  | 完全还原          |

> **收藏夹格式**：轻档的 HTML 导出为 **Netscape Bookmark File 格式**（HTML 收藏夹文件），Chrome / Edge / Firefox 均可直接导入为浏览器收藏夹（"收藏夹"为浏览器界面术语，本产品动作统一称"保存"）。

### 4.6.2 导出筛选

支持按范围：全部、按文件夹、按标签、按状态、按时间范围。

### 4.6.3 单条内容信息导出

对**单个网页**的内容信息（Snapshot 网页快照等 Archive 内容；Reader 阅读版属远期规划）按需导出：

- **先选内容，再选格式**（内容与格式解耦，任意组合）：

  - 内容（打包什么）：Snapshot 原始网页快照 / 该书签关联的全部内容信息（Reader 阅读版正文为远期规划）

  - 格式（导出成什么）：HTML / PDF / Markdown

- **导出示例**：

  - 网页快照 → HTML（保留原始网页结构）/ PDF

  - 阅读版正文（远期规划）→ Markdown / PDF / HTML

- 用于单篇存档、分享、离线保存；与 §4.6.1 的批量三档备份互不替代

# 05. 数据与同步

## 5.1 数据分层（方向性）

> 分层方向已定：结构化数据（Bookmark 核心、轻量，随需提取）与内容数据（Snapshot 等，按需归档）分开放置；具体存储形态、落点与选型待技术方案阶段确定。下方为当前方向示意，不作定稿。

```
应用数据库（结构化数据，方向示意）
├── Bookmark 表（结构化，轻量）
├── Scene 表（可配置数据，非固定枚举，见 2.0.1）
├── Archive Job 表（任务队列）
├── Archive Record 表（归档记录）
│   ├── 记录 parser / parser_version
│   ├── 记录 source（server/browser/manual）
│   └── 记录 storage_location（内容存储位置，指向内容存储层）
├── 配置与偏好
└── 操作日志

内容存储层（内容数据，形态待定：可选对象存储等，可按目标拆分 / 多目标并存）
└── Snapshot / Reader 归档内容
```

## 5.2 数据通道（范围）

产品范围如下，**实现方式不在本文规定**（现行技术方案待重建）：

- 不接任何第三方，产品完整可用
- 数据管理可选：**Raindrop**、**S3**、**WebDAV** 等
- Raindrop：**输入源**和/或**导出方向**，不是默认双向同步
  - 输入：首次可进 Inbox 或保持原路径；首次梳理后，新来的零散记录进 Inbox。不把对方数据变成 Scene
  - 导出：Link 级存档；不带 Scene 等使用场景；回收站默认不进存档
- 能连上本应用即可保存；第三方未配置或中断不阻塞保存（§5.2.3）

### 5.2.3 保存前提与临时保存

**能连上本应用即可保存**。不要求 Raindrop、S3、WebDAV 或其它第三方当时可用；中断时先写在应用内，恢复后再做已配置的导出。应用不可达时，本版不承诺仍能完成保存。

## 5.3 内容存储（方向性）

**分层存储**：结构化数据与内容数据分处两类存储、互不依赖。分层方向已定，具体存储形态与选型待技术方案阶段确定。

- **结构化数据**：Bookmark、Job、Record 等轻量记录，随需提取，存于应用数据库（端侧/服务端落点与具体引擎待定）

- **内容数据**：Reader HTML、Snapshot 资源等大文件，按需归档，与结构化数据分开放置；具体存储形态（如对象存储）与选型待技术方案阶段确定

**存储解耦（方向）**：

- 数据不依赖单一渠道，任一存储/渠道故障不影响核心"链接保存"与数据安全；Raindrop 仅为同步备份手段之一，见 §1.1

- 若采用对象存储，倾向以统一接口（如 S3 API）抽象，便于 R2 / MinIO / 任意 S3 兼容服务互换——此为方向性表述，待技术方案阶段确定

- 是否支持多目标并存、冗余份数与写入/校验策略等技术细节，均待技术方案阶段确定

# 06. 安全与约束

## 6.1 AI 操作边界

| 类别       | 策略                                      |
| -------- | --------------------------------------- |
| **禁止执行** | 删除 Bookmark、删除 Archive、修改文件夹结构、批量操作（默认）、未经确认的自动分流（改 Scene/Folder/Tag） |
| **允许执行** | 保存新链接、搜索列出、单条修改、获取统计、触发单条 Archive       |
| **建议先行** | Scene / Folder / Tag / 标题 / 描述等理解类产出，以"建议"呈现，用户确认后生效（可一键采纳/批量采纳） |
| **限速**   | 连续写入超阈值触发提示                             |

**可追溯与撤销**：AI 发起的写操作全部记入操作日志；用户可查看 AI 做了什么、并批量撤销（见 §6.2）。AI 判断错误不应破坏用户原有信息结构——默认不授予 AI 结构性改动（如批量重排 Scene / 重构文件夹）能力；若未来提供，需显式开启且受限。

## 6.2 兜底机制

- **软删除**：标记删除后进入回收站，周期内可一键恢复。导出 Raindrop 存档默认不含回收站条目

- **操作日志**：记录所有写操作，有容量与时限约束，支持清理/导出/循环覆盖

- **撤销**：工作台底部撤销提示

- **冲突处理**：本地与外部冲突时以本地为准，提供手动合并选项

## 6.3 隐私

- 私密文件夹/标签可标记，导航页默认不展示

- 查看私密内容需解锁

- 隐私内容可标记不进入 AI 记忆

- 公网部署需鉴权，本地部署也需考虑隐私页面保存

- **导航页匿名访问的范围控制**：第一版默认需要登录。若后续开放匿名访问，仅限已被规则/工具圈进导航的条目（标题 / 图标 / URL），Inbox 与私密内容不可见（纳入 §09 待决策）

# 07. 性能要求

## 7.1 原则

- **核心优先**：工作台保存、Agent 保存、工作台列表/搜索、导航页网页形态。插件与 Snapshot 截取不得拖慢「只存 Link」

- **非核心不增负**：Archive Job、小组件、统计、检测等非核心功能不得对核心路径造成可感知负担

- **可精简**：必要时可对非核心功能降级或精简，需确认后执行

- **容量基线**：性能设计按 600 条 Bookmark 考核首屏与检索；**这是性能基线，不是产品条数上限**。长期资料与 Rediscover 按可超过该规模预留，超基线时允许非核心功能降级，但保存与搜索不得失败

- **网络延迟补偿（设计导向）**：默认部署在境外边缘节点，国内访问存在客观延迟。性能设计以**分级按需加载**与**本地缓存优先**弥补——首屏读本地缓存做到零网络请求，重资源（Snapshot 内容、封面、统计）按需或懒加载，非核心功能不得占用核心路径的网络预算

- **同步可观测**：未推送 / 同步中的条目数量须在界面可见，用户能判断数据是否已落到真源

## 7.2 考核方向

- **页面响应**：导航页首屏、工作台视图切换、整理模式切换、搜索下拉等

- **数据读写**：本地读取/写入/批量操作、同步推送/拉取、导入/导出

- **同步速率**：记录本地 ↔ 外部同步的条数/秒、时延、成功率、队列长度

## 7.3 性能可观测（方向性）

不预设硬性验收阈值——速度与设备、网络强相关，难以用统一数值判定「合理」。方向是**用数据反映现状**，而非用阈值卡验收：

- **内置轻量性能检测**：记录首屏耗时、接口时延、同步耗时等指标，在设置页以面板呈现，供用户判断卡顿来自网络还是数据量
- **同步状态可观测**：未推送条数、队列长度、失败重试次数在界面可见
- 上述指标同时作为「是否需要降级非核心功能」的判断依据，具体埋点与呈现方式见技术方案

## 8.x 技术路线（暂定 · **非需求源**）

> 本节不是需求。产品已定：默认 Cloudflare Workers，其次 Docker；多端走该部署；备份兜底。下列框架/存储引擎名单供技术方案讨论，冲突时以 §8.1 / 技术方案为准，不以本节约束拆解。
>
> ⚠️ **过期提示（v1.0.7 后补注）**：本节部分条目已被现行 [技术总纲 v1.0_DeepSeek](../docs/DogEar_折耳书签_技术总纲_v1.0_DeepSeek.md) 取代或推翻（React 版本见 §4.1、推送窗口见 §6.6、Snapshot 生成位置见 §6.4 等）。凡与总纲冲突处一律以总纲为准，本节不再作为选型依据。

### 8.x.1 总体原则

- **Cloudflare Workers 优先**：一键部署，脚本自动创建 D1/R2/KV 等资源，零前置配置（R2 为内容存储默认实现，经 S3 API 可替换为其他 S3 兼容服务，见 §8.x.3）

- **Docker 兼顾**：同一份代码/配置能在本地/服务器运行

- **节省资源**：少请求、少带宽、少计算时长，批量操作、增量更新、懒加载

- **最小资源调取**：局部刷新、按需订阅，一点改动不影响全局加载

### 8.x.2 部署层（暂定）

| 方向        | 说明                                                   |
| --------- | ---------------------------------------------------- |
| 一键部署      | Wrangler CLI 脚本自动创建 D1 数据库、R2 bucket、自定义域名           |
| 双轨关系      | **Workers 轨与 Docker 轨二选一，互不级联**。用户选定一种部署方式，不需要同时维护两套 |
| Docker 兼顾 | 本地开发可用 `wrangler dev` 模拟 Workers 环境；生产 Docker 部署为独立轨 |
| 资源初始化     | 部署脚本通过 Cloudflare API 自动初始化，用户只需一个 Token             |
| 前端部署      | Workers Pages（同域名，无 CORS）                            |

### 8.x.3 数据层：分层存储（暂定）

| 层级        | 存储                                     | 用途                               | 策略                                                   |
| --------- | -------------------------------------- | -------------------------------- | ---------------------------------------------------- |
| **端侧缓存**  | **IndexedDB**                          | 首屏数据、离线浏览、本地整理                   | 首屏零网络请求；变更后同步到服务端真源；离线可整理，联网后对账                      |
| **服务端真源** | **D1** (Workers) / **SQLite** (Docker) | Bookmark 元数据、Archive Job 队列、操作日志 | 批量写入（多值 INSERT），游标分页避免 OFFSET                        |
| **内容存储**  | **R2 / S3 兼容（可换）**                     | Reader HTML、Snapshot 资源、备份文件     | S3 API 为统一接口，多目标并存（默认双份冗余）；零出口费，内容压缩（gzip/brotli）后存储 |
| **预留**    | **KV**                                 | 暂不绑定，未来用于边缘缓存或多实例场景              | —                                                    |

**端侧缓存架构**：

```
设备A IndexedDB ─┐
                  ├─→ 服务端 D1/SQLite（真源） → 内容存 S3 兼容对象存储（可多目标） / Link 可选通 Raindrop
设备B IndexedDB ─┘          ↑
                    工作台/导航页/扩展
```

- 首屏从 IndexedDB 读取，零网络请求

- 用户操作先写 IndexedDB 即时响应，再异步同步到服务端

- 离线时可浏览和整理，联网后自动对账

- Chrome 扩展与工作台同域时共享 IndexedDB |

### 8.x.4 同步层（暂定）

- **推送**：30 秒合并窗口，本地变更攒一批再推 Raindrop

- **拉取**：用 Raindrop `lastUpdate` 字段做增量，不拉全量

- **冲突**：本地优先，冲突项存临时表，不阻塞主流程

- **限频**：Raindrop API 429 时指数退避，本地队列持久化到 D1

- **实时推送**：Workers Cron Trigger（定时），不用 Durable Objects（成本考量）

### 8.x.5 服务端（暂定）

**不纳入核心过关**：浏览器插件（保存或新标签页）；看板 / 标签聚合 / 独立整理模式 / 死链统计；移动端；Reader / 手动选正文 / 高亮；自然语言检索；URL 去重；Primary Scene；Raindrop 双向同步；把 Scene 写入 Raindrop。Snapshot **截取失败不挡过关**（Link 必须成功）。

## B.1 概述

当前版本归档能力以 **Snapshot（网页快照）** 为主，**Reader（清洗阅读）及其关联能力整体后置**，作为远景规划。后置原因：Snapshot 实现更简单、保真度高、天然满足"内容不丢失"；Reader 需要长期维护内容解析器与站点规则，且其编辑能力技术成本不确定。

后置不代表放弃，以下细节全部保留，后续按需评估引入。

## B.2 Reader：清洗阅读版（远景规划）

**定位**：将网页清洗为"可读的文章"，是未来可能提供的内容阅读能力。**Reader 不是 DogEar 当前的核心产品定义**——它属于远景规划中的内容消费能力，不改变 Bookmark-first 定位。与 Snapshot 的差异：Reader 是"保存内容"，Snapshot 是"保存网页"，二者不互相替代。

> 当前阶段的网页内容提取（若需要）主要服务于：帮助 AI 理解 Bookmark、帮助生成 Metadata、帮助 Scene 分流、帮助 Snapshot、帮助未来 Reader——而不是要求用户进入 Reader 阅读（见 §1.4/§2.4）。

| 维度    | 描述                        |
| ----- | ------------------------- |
| 目标    | 长期舒适阅读                    |
| 内容    | 清洗后的正文 + 必要资源（图片等）        |
| 触发    | 用户主动 / 策略自动               |
| 存储与同步 | 内容存储层，不入 Raindrop（见 §5.3） |

**内容提取策略（远期）**：

采用多级解析和降级策略，不依赖单一方案：

```
URL / DOM
    │
    ▼
Primary Content Parser（通用解析）
    │
    ├── 成功 → Clean HTML
    │
    └── 失败
          │
          ▼
    Site-specific Rules（特定网站规则）
          │
          ├── 成功 → Clean HTML
          │
          └── 失败
                │
                ▼
          Browser Manual Select（用户手动选择正文区域）
                │
                ├── 成功 → 基于选中区域生成 Reader
                │
                └── 仍失败 → 保留 Original URL，Bookmark 不受影响
```

**Reader 编辑能力（远景规划）**：

- 若技术成本可控：支持轻量编辑（如高亮、批注、简单修正）

- 若技术成本高：仅支持读取、下载、上传替换、重新抓取

## B.3 Snapshot 后续增强（近期 / 远景）

- **Snapshot 阅读视图**（远景）：基于快照生成近似原网页的阅读/浏览视图（当前以原始网页形态展示，后续可增强）

- **更完善的 Archive**（近期）：Snapshot 生成可靠性、失败重试与批量归档策略增强

- **Markdown 轻量剪藏**（远景）：仅图文、无重附件的 Markdown 剪藏形态（原 A.9#1 表述：后续可能延伸 Markdown 轻量剪藏）

## B.4 关联功能（远景规划）

- **手动选择正文区域**：自动解析失败或结果不可靠时的兜底方案，基于选中区域生成 Reader（见 B.2）

- **Agent 保存后自动触发 Reader（后台策略）**：可配置，Agent 创建 Bookmark 后按策略异步生成 Reader

- **批量 Archive（Reader）**：对多选书签批量触发 Reader 归档

- **内容信息导出增强**：Reader 阅读版正文 → Markdown / PDF / HTML 导出

- **中档备份增强**：`Link + 个性化配置 + Reader`，导入可还原核心体验

- **更高级的 AI 能力**：AI 自动分流（显式开启+可追溯）、AI 推荐重新查看等（见 §4.5/§6.1，近期或远景视成熟度评估）

- **内容存储多目标增强**：在分层存储方向下，若后续采用 S3 兼容对象存储，进一步细化多目标同步策略、校验与自动容灾（具体选型与冗余策略见 §5.3，当前待定）

## B.5 引入时机与评估标准

- 当用户对"清爽阅读体验"有明确需求，或快照原貌形态不足以支撑阅读场景时，评估引入 Reader（远景规划）

- 引入前需评估：内容解析器与站点规则的长期维护成本、编辑能力技术成本、存储成本

- 引入时按"仅只读 → 轻量编辑"分阶段推进，避免一次投入过大

- Rediscover 系列（近期需求）的引入：先保证访问记录已记；卡片与回顾在核心框架稳定后再评估（§4.5）

| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 核心需求 / 近期需求 / 远景规划 | 需求分层的三层：核心＝基础框架必须具备；近期＝核心完善后扩展；远景＝产品具备形态后再评估。本文不用 P0/P1/P2（§1.2） |
| 远期          | **时间描述**：指某项能力中更靠后的阶段，或比远景更晚。不构成独立分层，也不改变所属分层（§1.2 术语口径） |
| Bookmark    | 长期存在的网页引用对象，核心是书签地址；以 Bookmark-first 组织一切（§1.1）                                                                                                                                 |
| Scene       | 使用情境（Why/When）；可多属、可扩展；Capture 不强制；Inbox 不强制转出；默认预设四场景，见 §2.0.1–§2.0.4                                                                    |
| AERR        | 系统内部行为原型 Action / Explore / Read / Reference，不直接展示给用户；用于默认工作台行为（§2.0.3）                                                                    |
| Status      | 书签的当前处理状态：待处理（Inbox）/ 已确认 / 搁置；底层字段 `unread` / `saved` / `archived`；与 Scene 解耦，且不等于内容 Archive（§2.1.1）                                                                 |
| Folder / Tag | 物理/逻辑归放位置 / 主题内容标识，与 Scene/Status 独立组合（§2.0）                                                                                                                                  |
| Archive     | 网页内容的异步副本（Snapshot 当前 / Reader 远期），定位为"内容保存/长期保全"层                                                                                                                              |
| Archive Job | 独立的归档任务，支持多来源和失败重试                                                                                                                                                           |
| Link        | 仅保存 URL 和 Metadata 的轻量书签，Bookmark 的基础形态                                                                                                                                          |
| Reader      | 清洗后的网页正文（远景规划中的内容阅读能力，非当前核心定位，见附录 B）                                                                                                                                          |
| Snapshot    | 尽可能还原原网页的完整存档，定位为 Preservation/Archive（网页内容长效保全），非阅读器                                                                                                                           |
| 剪藏          | 历史用语，指把网页正文/快照存为内容信息。当前版本不作为产品动作名；对应能力分别称为 Snapshot（当前）与 Reader（远期）                                                                                            |
| Capture     | 保存动作：以"零成本"将链接保存为 Bookmark，无需即时分类（§3.1）                                                                                                                                       |
| Organize    | 管理动作：系统理解书签用途与上下文，辅助场景化分流；用户按需管理（§1.1）                                                                                                                                      |
| Rediscover  | 重新发现：让过去收藏的内容重新进入用户视野（搜索/场景/最近收藏/历史访问/长期资料/相关与相似/AI 推荐），一级产品目标（§4.5）                                                                                                     |
| Inbox / 待处理  | 待处理书签的产品概念（底层 `unread` 字段），表达「尚未决定下一步怎么处理」，非「未阅读」；可长期停留，不限制 Scene/Folder/Tag（§2.1.1）                                                                                                                   |
| 导入梳理页      | 将 Raindrop 等输入源首次导入后，复用整理模式做一次快速过库的可选页面（§3.0），非强制关卡                                                                                                                               |
| 输入源 / 导出方向 | Raindrop 等第三方的两种用法：导入已有库，或把 Link 级记录写成存档；不是默认双向同步（§3.0 / §5.2）                                                                                                                              |
| 访问记录        | 核心需求：记录打开书签的行为，供最近访问 / 长期未访问；字段与界面后定（§4.5）                                                                                                                                                  |
| S3 兼容存储     | 以 S3 API 为统一接口的对象存储（R2 / MinIO / 任意 S3 兼容服务），内容存储层的候选实现之一（可多目标并存）；方向性表述，选型待技术方案阶段确定（见 §5.3）                                                                                  |
| 基础属性        | 随链接保存、以 Raindrop 官方 API 为字段基准的网页属性（URL / Title / Tags / Collection / Excerpt / Cover / Important 等），是保存书签时即具备、一般不变的信息；分 Raindrop 同构（可同步）与本地扩展抓取（仅存本地）两组，明细见[技术总纲 §5.7](../docs/DogEar_折耳书签_技术总纲_v1.0_DeepSeek.md) |

| 内容信息        | 链接背后需要固化的内容，即 Snapshot / Reader 等 Archive 内容，可随时间更新或被用户修改（原"高级信息"）；存于内容存储层，不入 Raindrop（见 §5.3）                                                                               |

| 已确认          | 状态之一（底层 `saved`）：整理后确认值得保留                                                                                                                              |

| 收藏标星        | 对书签打上标星（`important`），标记为个人收藏；与三态独立，交互形态为标星（非红心）                                                                                                                              |
| 应用 ID / Raindrop ID | **双 ID**：应用 ID 由本应用自维护（本地新录入、尚未推送真源前用 `tmp_` 前缀，推送成功后回填正式 ID）；`raindropId` 记录该书签在 Raindrop 侧的 `_id`，仅启用该通道时存在，同步时作为参数传出用于数据匹配 |
| Raindrop    | Raindrop.io；数据管理选项之一，可作输入源和/或导出存档方向，非产品依赖                                                                                                                                                    |
| Skill API   | 暴露给 AI 平台的能力接口，自描述、可被任何支持 tool calling 的 AI 调用                                                                                                                               |
| 工作台         | 独立 Web 界面，用于书签的收藏、管理、搜索、编辑（需登录）                                                                                                                                              |

| 导航页         | Bookmark 的访问/展示/重新发现层（非另一管理器）；第一版默认登录；展示范围由规则或工具圈定（全部 / 按规则-或 / 自定义搜索勾选 / 隐藏），非逐条点选（§4.3）                                                                                                             |
