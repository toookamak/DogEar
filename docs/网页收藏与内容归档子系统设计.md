# 网页收藏与内容归档子系统设计

> 文档定位：项目中的「网页收藏 / 内容归档」子系统设计  
> 当前重点：架构、数据模型、归档流程、内容提取策略与技术选型  
> 本文不涵盖整个项目的完整产品设计，仅定义网页收藏与归档相关的基础能力。

---

## 1. 背景与目标

本项目需要提供类似 Raindrop 的网页收藏能力，但不希望收藏内容仅停留在：

- URL
- 标题
- 网站
- 简略描述
- 缩略图

而是希望根据不同场景，允许用户或 Agent 在不同时间保存网页的实际内容。

目标包括：

1. 可以仅保存网页链接和基础 Metadata。
2. 可以保存经过清洗、适合长期阅读的网页正文。
3. 可以在必要时保存尽可能还原原网页布局和样式的网页快照。
4. 网页内容的保存不要求必须发生在第一次收藏时。
5. 收藏可以来自 Agent、浏览器或后台任务。
6. 同一个 Bookmark 可以在之后不断增加不同类型的归档内容。
7. 优先利用用户浏览器已经成功访问和渲染的页面，减少服务器直接抓取导致的失败。
8. 内容提取失败时，不影响 Bookmark 本身。
9. 不依赖单一网页解析方案，而采用多级解析和降级策略。
10. 尽可能保留原始内容，同时提供清爽、结构化的阅读版本。

---

# 2. 核心设计原则

## 2.1 Bookmark 与 Archive 完全解耦

不要把：

> 收藏 = URL + 网页内容

作为数据模型。

应该定义为：

> **Bookmark 是一个长期存在的网页引用对象，Archive 是可以异步产生的内容副本。**

基本关系：

```text
Bookmark
│
├── URL
├── Metadata
├── Tags
├── Folder
├── Notes
│
└── Archives
     ├── Reader
     ├── Snapshot
     └── 其他归档类型
```

因此，创建 Bookmark 时不要求一定完成网页内容抓取。

例如：

```text
Bookmark #1234
URL: https://example.com/article
Archive:
    Reader:   未保存
    Snapshot: 未保存
```

之后可以独立产生：

```text
Bookmark #1234
Archive:
    Reader:   已保存
    Snapshot: 未保存
```

甚至进一步：

```text
Bookmark #1234
Archive:
    Reader:   已保存
    Snapshot: 已保存
```

---

# 3. 为什么必须解耦

网页收藏的实际使用场景并不只有一种。

## 3.1 Agent 发现网页

Agent 可能发现一个值得收藏的网页：

```text
Agent
  ↓
提交 URL
  ↓
创建 Bookmark
```

此时 Agent 不一定拥有完整网页内容，也不一定需要立即保存内容。

因此可以先：

```text
Bookmark
├── URL
├── 基础 Metadata
└── Archive = pending / none
```

之后再由后台任务或者用户浏览器完成归档。

---

## 3.2 用户通过浏览器收藏

用户正在浏览网页：

```text
网页
 ↓
浏览器已经完成访问、JS 执行和渲染
 ↓
Browser Extension
 ↓
创建 / 更新 Bookmark
```

这种情况下可以直接利用当前页面 DOM 进行内容提取。

优势是页面已经在用户正常的浏览环境中成功打开。

---

## 3.3 用户之后才决定保存内容

用户可能第一次只收藏链接：

```text
Day 1
收藏 URL
```

几天后觉得网页很重要：

```text
Day 3
打开原网页
 ↓
点击“保存阅读版”
```

或者：

```text
点击“保存网页快照”
```

因此：

> **“收藏网页”和“保存网页内容”必须是两个独立操作。**

---

# 4. 三种主要保存模式

建议至少定义三种保存级别。

## 4.1 Link：链接收藏

最轻量的收藏模式。

保存：

```text
URL
Title
Site
Favicon
Description
Author
Published At
Cover
Tags
Created At
```

特点：

- 成本最低
- 几乎立即完成
- 不需要保存正文
- 适合普通收藏

对应传统 Bookmark Manager 的核心能力。

---

## 4.2 Reader：清爽阅读版

目标：

> 保存网页的主要内容，并去除与阅读无关的网页元素。

处理过程：

```text
网页
 ↓
获取 DOM
 ↓
正文识别
 ↓
内容清洗
 ↓
结构标准化
 ↓
保存 Clean HTML
```

应该尽可能保留：

- 标题
- 标题层级
- 段落
- 图片
- 图片说明
- 引用
- 列表
- 代码块
- 表格
- 链接
- 脚注
- 作者
- 发布时间

同时去除：

- 广告
- 导航栏
- 评论
- 推荐内容
- 页脚
- Sidebar
- Tracking
- 与正文无关的 UI

Reader 的目标不是还原网页，而是：

> **让用户以后仍然可以舒适地阅读这篇内容。**

---

## 4.3 Snapshot：网页快照

目标：

> 尽可能保存用户收藏时看到的网页本身。

保存对象包括：

- HTML
- CSS
- 图片
- 字体
- 必要资源
- 部分 JavaScript
- iframe 等资源

理想结果：

```text
snapshot.html
assets/
    image-001.webp
    image-002.webp
    font-001.woff2
```

用户之后打开 Snapshot：

```text
Snapshot
 ↓
尽可能还原收藏时的网页
```

Snapshot 特别适合：

- 网页设计案例
- 产品页面
- Wiki
- 数据可视化
- 游戏资料
- 页面布局本身有价值的网页
- 可能会发生较大变化的网页
- 用户希望长期保留原貌的网页

---

# 5. Reader 与 Snapshot 的区别

二者不应该互相替代。

| | Reader | Snapshot |
|---|---|---|
| 主要目标 | 长期阅读 | 网页存档 |
| 内容 | 正文 | 整个网页 |
| 页面结构 | 清爽化 | 尽可能还原 |
| 广告 | 删除 | 尽可能保留/根据策略处理 |
| 导航 | 删除 | 尽可能保留 |
| CSS | 简化/重新渲染 | 尽可能保留 |
| JS | 通常不需要 | 必要时保留 |
| 文件大小 | 较小 | 较大 |
| 适合搜索 | 非常适合 | 较差 |
| 适合 AI/RAG | 非常适合 | 较差 |
| 适合离线阅读 | ✅ | ✅ |
| 适合网页长期存档 | 一般 | **非常适合** |

因此：

> **Reader 是“保存内容”，Snapshot 是“保存网页”。**

# 6. 推荐的总体架构

网页收藏与归档子系统建议采用以下结构：

```text
                         用户 / Agent
                              │
               ┌──────────────┼──────────────┐
               │              │              │
               ▼              ▼              ▼
            Browser          Agent         Server
            Extension        API           Worker
               │              │              │
               └──────────────┼──────────────┘
                              ▼
                         Bookmark API
                              │
                              ▼
                         ┌─────────┐
                         │ Bookmark│
                         └────┬────┘
                              │
                       Archive Jobs
                              │
          ┌───────────────────┼──────────────────┐
          │                   │                  │
          ▼                   ▼                  ▼
      Metadata              Reader           Snapshot
          │                   │                  │
          │             ┌─────┴─────┐            │
          │             │           │            │
          │          Defuddle    Template     Snapshot
          │         /Readability   Rules       Engine
          │             │           │            │
          │             └─────┬─────┘            │
          │                   │                  │
          └───────────────────┼──────────────────┘
                              ▼
                     Archive Storage Layer
                         │             │
                         ▼             ▼
                        D1             R2
                     Metadata        Content
                     Index           Images
                                     Snapshot
                                     Assets
```

# 7. Archive Job：整个架构的关键抽象

不应该把“抓取网页”设计成 Bookmark 的一个属性。

应该设计为独立的：

> **Archive Job**

例如：

```text
ArchiveJob
├── id
├── bookmark_id
├── type
├── source
├── status
├── created_at
├── started_at
├── completed_at
├── error
└── result
```

其中：

### type

```text
metadata
reader
snapshot
assets
```

### source

```text
agent
browser
server
manual
```

### status

```text
pending
processing
completed
failed
cancelled
```

---

# 8. 一个 Bookmark 可以对应多个 Archive Job

例如：

```text
Bookmark #1234
│
├── Metadata Job
│     └── Server → completed
│
├── Reader Job
│     └── Browser → completed
│
└── Snapshot Job
      └── Browser → completed
```

这意味着同一个 Bookmark 可以经历多次处理。

例如：

```text
第一次：
Server → Reader → failed

第二次：
用户打开网页
Browser Extension → Reader → success

第三次：
用户点击保存快照
Browser Extension → Snapshot → success
```

Bookmark 本身始终存在。

---

# 9. 多来源内容获取策略

不应该只依赖服务器抓取。

建议支持三个主要来源。

## 9.1 Server Fetch

服务器直接访问 URL：

```text
URL
 ↓
HTTP Fetch
 ↓
HTML
 ↓
Parser
```

优点：

- 自动
- 不需要用户操作
- 适合批量处理
- 适合 Agent 收藏后自动生成 Reader

缺点：

- Cloudflare / WAF
- JavaScript Challenge
- 登录状态
- Cookie
- 动态页面
- 地区限制
- Bot Detection

都可能导致失败。

---

## 9.2 Browser Fetch

用户已经正常打开网页：

```text
Browser
 ↓
网页已经完成渲染
 ↓
Extension
 ↓
获取当前 DOM
 ↓
Parser
```

这是本系统非常重要的能力。

因为用户浏览器已经完成：

- TLS
- Cookie
- 登录
- JavaScript
- 页面渲染
- 图片加载
- 网站访问验证

因此 Extension 不需要再让服务器从零访问这个网页。

这种模式不是为了破解网站访问控制，而是利用用户已经正常访问的页面完成本地剪藏。

对于 CAPTCHA、登录限制、付费权限以及明确的访问控制，不应该尝试绕过。

---

## 9.3 Agent Fetch

Agent 可以创建 Bookmark：

```text
Agent
 ↓
POST /bookmarks
 ↓
Bookmark Created
```

然后：

```text
Archive Policy
 ↓
Server Job
```

或者只等待以后用户处理。

---

# 10. 推荐的多级内容提取策略

不要只依赖一个 Parser。

建议：

```text
                URL / DOM
                   │
                   ▼
           Primary Content Parser
                   │
             ┌─────┴─────┐
             │           │
           成功          失败
             │           │
             ▼           ▼
         Clean HTML   Secondary Parser
                         │
                    ┌────┴────┐
                    │         │
                  成功        失败
                    │         │
                    ▼         ▼
                Site Rule   Manual Select
                              │
                              ▼
                         User Browser
```

更具体可以设计成：

```text
Browser / Server
       ↓
Rendered HTML
       ↓
Defuddle / Readability
       ↓
Site-specific Template
       ↓
Content Normalization
       ↓
Clean HTML
```

如果仍然失败：

```text
用户手动选择正文区域
```

最后仍然保留：

```text
Original URL
```

如果用户明确要求完整保存：

```text
Snapshot
```

---

# 11. Defuddle 的职责

Defuddle 更适合作为：

> **通用网页正文解析层。**

它负责：

```text
HTML / DOM
 ↓
正文识别
 ↓
杂项清理
 ↓
Metadata
 ↓
Clean HTML / Markdown
```

适合输出：

```json
{
  "title": "...",
  "author": "...",
  "description": "...",
  "image": "...",
  "published": "...",
  "content": "..."
}
```

它应该位于系统的：

```text
Content Extraction Layer
```

而不是整个 Bookmark 系统的上层。

---

# 12. clipper-templates 的职责

`clipper-templates` 更适合作为：

> **网站专用内容规则参考库。**

普通网页：

```text
URL
 ↓
Defuddle
 ↓
Reader
```

特殊网站：

```text
YouTube
 ↓
YouTube Template
 ↓
标题
作者
频道
发布时间
Transcript
缩略图
```

例如：

```text
GitHub
 ↓
GitHub Template
 ↓
Repository
Stars
Language
Description
README
```

因此 Template 的作用不是单纯重新排版，而是：

> **告诉系统“这个网站有哪些有价值的信息，以及应该如何组织这些信息”。**

最终可以形成统一的数据结构：

```json
{
  "title": "...",
  "url": "...",
  "site": "...",
  "author": "...",
  "published": "...",
  "description": "...",
  "cover": "...",
  "content": "...",
  "type": "article",
  "tags": []
}
```

特殊网站则可以增加额外字段。

---

# 13. Omnivore 的参考价值

Omnivore 最值得研究的不是整个产品，而是：

> **网页内容抓取、Readability 扩展以及 Reader 内容处理链。**

其核心思路可以概括为：

```text
Rendered Page
 ↓
Chromium / Browser
 ↓
Readability
 ↓
Omnivore 对 Readability 的扩展
 ↓
Content Cleaning
 ↓
Reader
```

这类架构特别适合解决：

- 动态网页
- 正文识别
- 标题层级
- 图片
- 引用
- 代码
- 阅读体验

等问题。

因此可以把 Omnivore 作为**内容解析与 Reader 设计的参考对象**。

如果直接移植其代码，则需要注意 Omnivore 项目的 AGPL-3.0 许可证。

---

# 14. SingleFile 的职责

SingleFile 适合作为：

> **Snapshot 层的参考或实现基础。**

它解决的是：

```text
Rendered Page
 ↓
HTML
CSS
Images
Fonts
Other Assets
 ↓
Self-contained HTML
```

这与 Reader 完全不同。

建议不要让 Snapshot 成为所有收藏的默认行为，因为完整网页可能非常大。

例如：

```text
1000 个网页
×
平均 5 MB
=
约 5 GB
```

如果页面存在大量图片、字体、脚本或其他资源，实际容量可能进一步增加。

因此 Snapshot 应该是：

> **用户主动选择的高成本归档模式。**

同时需要特别注意 SingleFile 使用 AGPL-3.0。如果直接集成其代码，需要对项目许可证兼容性进行评估。

---

# 15. 三种项目在系统中的位置

这几个开源项目不是简单的竞争关系。

推荐理解为：

```text
                   你的收藏系统
                         │
       ┌─────────────────┼──────────────────┐
       │                 │                  │
       ▼                 ▼                  ▼
    Bookmark           Reader            Snapshot
       │                 │                  │
       │          Defuddle / Readability   SingleFile
       │                 │
       │          clipper-templates
       │
       ▼
       D1
                         │
                         ▼
                        R2
```

对应关系：

| 项目 | 最适合参考的部分 |
|---|---|
| **Karakeep** | Bookmark / Archive / Search / AI 产品模型 |
| **Omnivore** | Reader / Content Fetch / Readability 扩展 |
| **Defuddle** | 独立网页正文解析库 |
| **clipper-templates** | 网站专用提取规则 |
| **SingleFile** | 完整网页 Snapshot |

# 16. 为什么不建议直接以某一个项目作为基础

## 不建议直接以 SingleFile 为核心

因为 SingleFile 的核心目标是：

> 完整网页归档。

它不是 Bookmark Database，也不是 Reader。

---

## 不建议直接以 clipper-templates 为核心

因为它主要是：

> 模板集合。

不是完整的剪藏程序。

---

## 不建议直接以 Defuddle 为核心

Defuddle 是：

> 内容解析基础设施。

它不负责：

- 收藏管理
- 用户账户
- 标签
- 文件夹
- 搜索
- Archive Job
- 存储

---

## 不建议直接 fork Web Clipper 作为整个系统

Web Clipper 已经具备比较完整的浏览器剪藏体验，但其设计重点是：

```text
网页
 ↓
Clipper
 ↓
各种第三方服务
```

而本系统需要：

```text
网页
 ↓
Bookmark
 ↓
可异步归档
 ↓
自己的 Storage
```

因此更适合研究其 Extension 和 Template 设计，而不是让其架构决定整个系统。

# 17. 推荐的异步闭环

完整过程可以设计为：

```text
                ┌─────────────────┐
                │ 创建 Bookmark   │
                └────────┬────────┘
                         │
                         ▼
                保存 URL + Metadata
                         │
                         ▼
                ┌─────────────────┐
                │ Archive Policy  │
                └────────┬────────┘
                         │
              ┌──────────┼──────────┐
              │          │          │
              ▼          ▼          ▼
            None       Reader     Snapshot
              │          │          │
              │          ▼          ▼
              │       Parse       Archive
              │          │          │
              │     ┌────┴────┐     │
              │     │         │     │
              │   Server    Browser  │
              │     │         │      │
              │     └────┬────┘      │
              │          │            │
              │          ▼            ▼
              │       Success      Success
              │          │            │
              └──────────┼────────────┘
                         ▼
                    Update Archive
                         │
                         ▼
                    D1 / R2
```

如果失败：

```text
Archive Job
     ↓
failed
     ↓
Bookmark 保留
     ↓
等待其他来源重新处理
```

例如：

```text
Server Reader
     ↓
failed

用户以后打开网页
     ↓
Browser Extension
     ↓
Reader
     ↓
success
```

这就是整个系统的核心闭环。

# 18. Archive 状态设计

Bookmark 页面应该能够区分不同内容的状态：

```text
Bookmark #1234

Link       ✓
Metadata   ✓
Reader     ✓
Snapshot   -
```

或者：

```text
Bookmark #5678

Link       ✓
Metadata   ✓
Reader     ✗
Snapshot   -
```

失败不代表 Bookmark 失败。

它只代表：

> **某一次 Archive Job 没有成功。**

# 19. 推荐的用户操作模型

浏览器 Extension 可以提供：

```text
┌─────────────────────────────┐
│ 保存网页                     │
├─────────────────────────────┤
│ ☑ 收藏链接                   │
│                             │
│ ○ 仅链接                     │
│ ○ 阅读版                     │
│ ○ 网页快照                   │
│ ○ 阅读版 + 网页快照          │
│                             │
│ 文件夹：技术 / AI            │
│ 标签：AI Cloudflare          │
│                             │
│             [保存]           │
└─────────────────────────────┘
```

但是默认不应该要求用户每次都选择。

建议：

```text
默认：
Link
```

重要内容：

```text
Reader
```

网页本身值得保留：

```text
Snapshot
```

# 20. 可以进一步增加 Reader + Assets 模式

Reader 不一定只能保存纯文本。

可以设计一个中间模式：

> **Reader + 必要资源**

保存：

```text
article.html
assets/
    image-001.webp
    image-002.webp
    image-003.webp
    font.woff2
```

但不保存：

```text
广告
网站导航
评论
Tracking
无关 JS
推荐内容
```

这样可以得到：

> **比 Snapshot 更轻、更干净，但比纯 Markdown 更完整的离线阅读版本。**

这个模式可能会成为实际使用频率最高的归档类型。

# 22. Bookmark 与 Archive 的推荐数据关系

概念模型：

```text
Bookmark
    │
    ├── Metadata
    │
    └── Archive[]
             │
             ├── Reader
             │     ├── content
             │     ├── assets
             │     └── metadata
             │
             └── Snapshot
                   ├── html
                   ├── assets
                   └── metadata
```

Archive 不应该直接覆盖 Bookmark。

每一次归档都可以保留：

```text
archive_id
bookmark_id
type
source
created_at
status
storage_location
parser
parser_version
```

这样以后可以知道：

> 这个内容是什么时候、通过什么方式、使用什么 Parser 保存的。

---

# 23. Parser Version 非常重要

网页解析器未来一定会变化。

例如：

```text
Defuddle v1
 ↓
Reader v2
```

如果不记录 Parser 版本，未来很难判断：

> 为什么同一个网页两次解析出来的内容不同？

因此 Archive Record 建议保存：

```text
parser = defuddle
parser_version = x.x.x
```

如果是网站专用规则：

```text
parser = template
template = youtube
template_version = x
```

如果是浏览器手动选择：

```text
source = browser
method = manual-selection
```

---

# 24. 内容提取失败时的策略

失败不能简单地返回：

```text
抓取失败
```

而应该保留上下文：

```text
ArchiveJob
status: failed

error:
    dynamic_page
    blocked
    timeout
    parser_failed
    unsupported_content
```

然后允许：

```text
Retry
```

或者：

```text
Open in Browser
```

用户打开网页以后：

```text
Save Reader
```

# 26. 为什么浏览器端应该成为重要的最终兜底

服务器抓取存在天然限制：

```text
Server
 ↓
网站
 ↓
可能被识别为 Bot
```

而用户浏览器：

```text
User Browser
 ↓
网站
 ↓
正常用户访问
```

因此本系统不应该试图通过不断升级爬虫手段来解决所有网站。

更合理的原则是：

> **服务器负责自动化，浏览器负责高成功率和高保真度。**

服务器：

- 自动抓取
- Agent 收藏后的后台处理
- Metadata
- 普通 Reader

浏览器：

- 动态网页
- 用户登录环境
- 当前 DOM
- Reader
- Snapshot
- 手动选择内容

# 27. 与 Raindrop 类产品的差异

传统 Bookmark Manager：

```text
URL
 ↓
Metadata
 ↓
收藏
```

本系统：

```text
URL
 ↓
Bookmark
 ↓
可以在未来任意时间增加：
    ├── Reader
    ├── Snapshot
    ├── Image Assets
    ├── PDF
    └── 其他归档
```

因此 Bookmark 是：

> **长期引用**

Archive 是：

> **可重复生成的内容副本**

这是整个架构最核心的抽象。

# 30. 核心结论

本系统不应该围绕：

> “如何做一个更强的 Web Clipper”

来设计。

而应该围绕：

> **“如何让一个 Bookmark 在不同时间、不同来源下逐步形成越来越完整的归档。”**

核心模型：

```text
Bookmark
    │
    ├── Link
    ├── Metadata
    │
    └── Archives
         ├── Reader
         ├── Snapshot
         └── Future Types
```

核心流程：

```text
创建 Bookmark
      ↓
立即保存链接
      ↓
可选 Metadata
      ↓
创建 Archive Job
      ↓
Server / Agent / Browser
      ↓
多级 Parser
      ↓
Reader / Snapshot
      ↓
D1 / R2
      ↓
Archive 状态更新
```

核心技术组合：

```text
Omnivore
    → 研究高质量 Reader / Content Fetch / Readability 扩展

Defuddle
    → 作为独立网页内容解析层

clipper-templates
    → 作为网站专用结构化提取规则的参考

SingleFile
    → 作为 Snapshot / 完整网页归档的参考

Karakeep
    → 研究 Bookmark + Archive + AI 的产品层设计
```

最终形成：

```text
                    Bookmark
                       │
             ┌─────────┴─────────┐
             │                   │
          Reader              Snapshot
             │                   │
       “保存内容”             “保存网页”
             │                   │
       Defuddle/Readability    Snapshot Engine
             │                   │
       Templates               R2
             │
             ▼
       清爽、可搜索、可阅读
```

**最重要的架构原则只有两个：**

1. **Bookmark 永久存在，Archive 可以异步产生、失败、重试和重复生成。**
2. **自动抓取与浏览器抓取是互补关系，而不是二选一。**

这样既允许 Agent 只提交一个 URL，也允许用户几天后通过浏览器补充 Reader 或 Snapshot，同时不会因为某一次网页解析失败而破坏收藏本身。
