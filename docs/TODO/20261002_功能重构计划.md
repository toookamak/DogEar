# 功能重构计划：Raindrop 整理台

---

## 0. 一句话

DogEar 不再做「一个不依赖 Raindrop 也能用的书签管理器」，改做**「把已有 Raindrop 收藏理顺的批量工具 + 打开就能搜全的本地索引」**。功能不是删出来的，是**换主流程**换出来的。

> **2026-10-02 方向修正（用户反馈后）**：主入口**不换成「哪里乱」**，仍以**全预览**为主；Raindrop 连接与配置**回设置页，不是必选门槛**。DogEar 的第一身份是**书签查询工具**，整理是叠加能力，不是替代。详见 §2 决策四、§3.1。

---

## 0.5 阻塞项：Raindrop 收藏夹与标签全链路断链（2026-10-02 核实）

**这是 P0。不修，下面的界面与流程都是空转。** 逐条读代码核实，非推测：

| 环节 | 实际状态 | 证据 |
| --- | --- | --- |
| 拉 · 标签 | `rd.tags` 数组**整个被丢弃**，既不落字段也不进 `raindropExtras` | `apps/server/src/channels/raindrop.ts:21-47` |
| 拉 · 收藏夹 | `collection.$id` 只塞进 `raindropExtras.collectionId`，**未映射到 `bookmarks.folder_id`**；拉回来的书签 `folderId` 恒为 null | 同上 · `packages/db/src/schema.ts:61` |
| 拉 · 收藏夹列表 / 标签表 | `getCollections()` / `getTags()` **已定义但全仓零调用**，收藏夹与标签清单从未拉取 | `raindrop.ts:194`、`:199` |
| 推 · 标签 | 消费器 payload 只装 `url/title/note`，`tags` 恒为 `undefined` | `apps/server/src/sync/consumer.ts:103-105` |
| 推 · 收藏夹 | `collection` 字段从 create 到 update 全程未出现 | 同上 |
| 导出 · 标签 | **硬编码 `tags: []`** | `apps/server/src/sync/raindrop-export.ts:74` |

测试未覆盖：fixture 的 `tags` 全为空数组、`collection.$id` 恒为 `-1`（Raindrop 的 Unsorted 默认值），故 CI 全绿不构成反证。

**根因**：同步设计 §3.1 定的 payload 契约为 `url / title / note / raindropId`——**契约本身漏了 folder 与 tag**，实现是如实的，是契约错了。

**两个待验证 / 待决策点**

1. **`PUT /raindrop/{id}` 的 `tags` 是部分更新还是整体替换？** 官方文档未写明（<https://developer.raindrop.io/v1/raindrops/single>）。若为替换语义，现有实现每次 update 只传 url/title/note，**可能清掉远端已有的收藏夹与标签**。**须用真实 token 实测一次再定修复方案**，不得凭文档措辞推断。
2. **改走批量接口。** Raindrop 支持 `PUT /raindrops/{collectionId}`，body 带 `ids` 数组，**单次最多 100 条**，可同时改 `collection` 与 `tags`；限流 120 请求/分钟（<https://developer.raindrop.io/v1/raindrops/multiple>）。现实现逐条 PUT，批量整理 200 条即撞限流。**改走批量接口是「批量整理」能力的前置条件**，不是优化项。批量 `tags` 语义为**追加**（空数组清空），与单条 PUT 需分别验证。

## 1. 为什么卡住（诊断）

不是功能不够，是**定位和你的实际处境对不上**。每条都能在代码和定稿里指认。

### 1.1 Raindrop 同时背了四个互相打架的角色

需求总纲 §1.1 定的是：

> 不依赖 Raindrop 即可完整使用。应用数据始终为真源。Raindrop、S3、WebDAV 等是数据管理选项（输入源和/或导出/备份方向），不是登录门槛。

于是 Raindrop 在产品里同时是：① 你既有的存量资产 ② 写回目标 ③ 一个可选数据通道 ④ 一个被明确声明「不是前提」的东西。**四个角色没有排过优先级，界面就只能把它们当同级按钮并排摆出来**——`apps/web/src/components/channels/ChannelManager.tsx:212-252` 那一行就是结果：导入 / 拉取 / 导出 / 编辑 / 删除，五个平级按钮。

所以「是否推送、如何推送、是否存储、如何存储」这四问在需求层就没有答案，界面写得再清楚也只是把选项摆给你自己猜。**这不是界面问题，是需求层没做决策。**

### 1.2 「不维护复杂体系」与「四维分类」自相矛盾

需求总纲 §1.1 核心问题第 2 条写「**不依赖用户长期维护复杂的文件夹和标签体系**；系统理解书签的用途与上下文」，紧接着 §2.0 定义了 Scene / Status / Folder / Tag 四个独立维度，全靠用户手工维护。

这套复杂度的原定泄压阀是 AI（「系统理解」）。但按 `AGENTS.md` 额外补充的开工口径，AI 建议四落点**目前全是占位 UI，无模型时返回空建议**。

结果：**本该由 AI 扛的认知负担原样落回用户手上，而泄压阀还是空的**。四维分类 + 四视图 + 八维筛选 + 三种状态，打开第一眼要理解十几个概念。这不是「功能庞大」，是**认知税前置、回报后置**。

### 1.3 投入全在「新收藏进来」，没人管「已有的几千条」

现有投入分布：工作台保存表单、浏览器扩展、Skill API、metadata 抓取、封面 R2、快照引擎——全在 Capture 一侧。`docs/TODO.md` 的 N1/N2/L2/L3 排的也都是这一侧的收尾。

但真实处境不是「我要存一个新链接」，而是「我那堆东西还是乱的」。**产品没有任何一个入口长得像「来看看你的收藏哪里乱」。**

### 1.4 决策面和使用面被拆开

设置页 6 个分区（状态 / 通道 / Agent / 外观 / 备份 / 日志 / 回收站）里藏着这个产品**真正的所有决策**：同步方向、导入、导出、备份、冲突。工作台是「用」的地方，设置页是「决定」的地方，两者不通。没有任何操作能形成「整理了 → 看到结果 → 放心了」的闭环。

### 1.5 检索现在搜不全（与「完整好查」直接冲突）

`apps/web/pages/WorkbenchPage.tsx:521` 传给 ⌘K 的是 `bookmarks={bookmarks}`，即**当前已加载的那一页列表**，不是全量。所以搜不到没被翻到过的收藏。需求总纲同时排除了全文正文索引。

3000 条规模下 MiniSearch 客户端全量索引完全够用（内存几 MB），**这是能修的，不是技术问题**。

## 2. 已拍板决策（2026-10-02）

### 决策一：数据流 = 拉下来改，改完回写

> Raindrop 作为输入源，Cloudflare（D1）作为存放。从 Raindrop 下载更新收藏，本地编辑好，CF 存一份，Raindrop 也更新。

**这在数据流层面与现有实现一致**——需求总纲定的就是「应用数据是真源，Raindrop 是双向通道」，`sync_queue` 整组已落地（`docs/TODO.md` L2 全勾）。

**但它不是纯存储问题。** 需要在文档层面说清的一点：

> 「本地改完 → Raindrop 也更新」这半句引入了一个必须被管理的状态：**这一条我改的，推了没有？**

这个状态在现状里就是顶栏那个「待同步 N」，而它恰恰是你最初说「体验不清晰」的来源之一。所以架构不用动，但**界面必须能回答「我改的东西到了没有」**。这是本轮重构的核心之一，不是存储细节。

因此 §3 把「拉取」和「回写」的时机、范围、失败可见性写成明确契约（见 3.2）。

### 决策二：Folder + Tag 为主，Scene 降级为本地维度，Status 隐藏

- **Folder / Tag**：主维度，与 Raindrop 概念一一对应，整理结果写回。
- **Scene**：保留，但降级为**本地维度**，界面明确标注「不写回 Raindrop」。定位从「四维之一」变成「一个可选的本地回顾视角」，侧栏降为次级分组。
- **Status**：**界面隐藏**。注意是隐藏，不是删除——`status` 字段（`unread` / `saved` / `archived`）、API、筛选参数、回收站全部保留原样，数据不动。留一个开关随时能回来。

### 决策三：本轮先出计划文档，界面代码不动

### 决策四：主入口仍是「全预览」，整理是叠加不是替代（2026-10-02 修正）

> 主入口不能换成「哪里乱」，还是以全预览为主……**不能影响全标签浏览，他还是会作为书签查询的工具。**

对 v0.1 的实质性纠正。v0.1 把「哪里乱」放成默认落点，隐含假设「用户来这里是为了整理」。实际不成立——**DogEar 的第一身份是书签查询工具**，整理是在浏览之上的叠加能力。

修正后的信息架构：

| 层 | 是什么 | 语义 |
| --- | --- | --- |
| 默认落点 | **全预览**（全部收藏） | 保持现状的浏览强度，不动 |
| 侧栏 | 全部 / 收藏夹 / 标签 | **主要浏览路径，维持现状** |
| 筛选 | 「未打标签」「没归类」等作为**无状态筛选条件**，收在筛选器里 | 是「缩小范围的手段」，不是「待办任务」 |
| 整理 | 一个**独立入口**（侧栏一项或工具栏一键） | 明确的动作区，与浏览区分开 |
| 搜索 | 全量、可直接操作 | 第一身份的核心能力 |

**关键区别**：无状态筛选只是过滤条件，**不带「这些是欠账」的道德感**。「未打标签」做成侧栏一级项配计数 812，读起来像 812 件欠债；做成筛选器里的一个条件，读起来只是「我想看看没打标签的有哪些」。

### 决策五：Raindrop 连接与配置回设置页，不做必选门槛（2026-10-02）

> Raindrop 的首次连接和配置等还是放在设置里，不要放在必选项。

这**撤销**了 v0.1 的「第一步连接 / OAuth 提到第一屏」方案，**同时撤销**了 §7 冲突表第 3 条（把需求总纲「首次使用不引导登录 Raindrop」反转）——**该项维持定稿原样，不动 wiki**。

保留 v0.1 方案里仍然成立的部分：连接入口**要明确、要能说清后果**（连了会发生什么、不连会怎样），只是位置在设置页，不是第一屏门槛。

### 决策六：S3 / WebDAV 保留不删（2026-10-02）

见 §4.4。

## 3. 需要写进定稿的契约（本轮不写代码，先把答案定下来）

### 3.1 主流程（按决策四、五修正）

**主路径 = 浏览与查询**（第一身份）：

| 步 | 用户在做什么 | 啊哈时刻 |
| --- | --- | --- |
| 1 浏览 | 打开就是全预览，按收藏夹 / 标签 / 时间自由下钻 | 「我的收藏全在这儿，随手能翻」 |
| 2 筛 | 需要时用无状态筛选缩小范围（未打标签、没归类…） | 「想看看没打标签的有哪些」 |
| 3 找 | 打开就搜全量，搜到直接改 | 「三秒找到半年前存过的那篇」 |

**叠加路径 = 整理**（第二身份，独立入口）：

| 步 | 用户在做什么 | 啊哈时刻 |
| --- | --- | --- |
| 1 进整理 | 从筛选结果或独立入口进入整理模式 | 「原来是这批需要理」 |
| 2 批量 | 多选 → 改收藏夹 / 加标签 / 移出 | 「一批 200 条，10 秒改完」 |
| 3 回写 | 后台自动推，状态可见可查 | 「推完了，失败 2 条，原因在这」 |

**连接 Raindrop 在设置页**，不在上述任一路径上作为门槛（决策五）。未连接时本地产能全部可用，只是看不到 Raindrop 存量、不能回写。

> **前置提醒**：以上全部以前置 §0.5 的断链修复为前提。当前收藏夹与标签既拉不到也推不回，整理路径无法真正闭环。

### 3.2 拉取契约

| 项 | 口径 |
| --- | --- |
| 首次 | OAuth 后自动全量拉取，页面显示进度，完成后直接进主列表 |
| 之后 | 手动「同步」按钮为主；是否加定时自动拉取见 §7 待拍板 |
| 分页 | 沿用现有单页 50 条防风控口径（同步设计 §3.2），全量循环由服务端驱动 |
| 去重 | 沿用现有 raindropId + URL 双重去重（v0.7.40） |

### 3.3 回写契约

| 项 | 口径 |
| --- | --- |
| 范围 | **Folder + Tag + title + note**。Scene / Status / 访问记录**不写回** |
| 时机 | 优先自动（`sync_queue` + Cron 已有），用户不需手动点「推送」 |
| 可见性 | 常驻一个明确状态：「N 条待回写 / 上次回写于 X / 失败 N 条（原因逐条可查）」 |

### 3.5 双向差异契约（2026-10-02 新增）

现状只有一个「待同步 N」，**它只代表「本地领先」**。「远端有、本地还没有」这个数字**根本不存在**——所以现状无法回答「Raindrop 那边变了什么」。

| 方向 | 含义 | 怎么算 | 现状 |
| --- | --- | --- | --- |
| **领先 ↑** | 本地改了、还没回写 | `sync_queue` 中 `pending` 条数 | **已有**，即现在的「待同步 N」 |
| **落后 ↓** | 远端有、本地还没有 | 需新增轻量探测，见下 | **不存在，要新建** |

**落后数的探测方案（关键取舍）**

| 方案 | 成本 | 准确度 | 裁决 |
| --- | --- | --- | --- |
| A. `远端 count − 本地 count` | 1 次调用 | **不准**：本地多的会把差值抵消，符号都可能反 | 不用 |
| B. 拉第一页 `sort=-lastUpdate&perpage=50` 比对本地 `raindropId` 集合 | 1 次调用，50 条 | **准**：Raindrop 按 lastUpdate 降序，新的必在首页；首页全已知 ⇒ 落后 0，有 N 个未知 ⇒ 落后 ≥ N | **采用** |
| C. 全量比对 | 69+ 页 | 准但违反 120 请求/分钟限流 | 不用 |

采用 B，并在语义上**如实标注下界**：探测出 5 条新书签时显示「↓ 5」，点下载继续按页拉取，**不谎称「一共就 5 条」**。

**明细的边界**（要说清，避免界面承诺做不到的事）：

- **领先的明细可以给全**：`sync_queue` 的 payload 里存了每次改了什么，聚合后能说出「8 条改了标签 · 4 条改了收藏夹 · 2 条改了标题」。
- **落后的明细只能给首屏**：那 5 条具体是什么，拉回来才知道。所以设计上点「查看」= 触发一次预览拉取并展示，不做「零成本预览远端变更列表」这种做不到的承诺。

**由此新增的接口**（须按 `AGENTS.md` 先确认再动）：

| 接口 | 用途 |
| --- | --- |
| `GET /api/sync/diff` | 返回 `{ ahead, behind, behindIsExact, aheadBreakdown, lastPushAt, lastPullAt, failed }`。内部只 1 次 Raindrop 调用 + 1 次本地查询 |
| `GET /api/sync/preview?direction=behind` | 按需拉回首屏供「查看」用，不落库 |
| 失败 | 必须指名道姓：哪一条、为什么、重试到第几次。不允许只弹一条 6 秒 toast（v0.7.50 已修一半，补完逐条可查） |
| 冲突 | 沿用现有「本地赢 + 记两端快照」；但冲突面板应出现在主流程而非设置页 |

### 3.4 状态与自动回写的关系（**需特别裁决**）

Status 隐藏后有个直接后果：现有 `unread` 是 Inbox 的来源，若用户无法把书签从 `unread` 移走，**Inbox 会无限膨胀**。

建议裁决：**Inbox 的职责由派生视图「还没归类的」接管**，不靠 `status` 值。派生视图是算出来的，不是存出来的，因此与 Status 隐藏不冲突。同时拉回的书签不再默认进 Inbox（避免存量一接进来就爆），直接进主列表。

此项列入 §7 待拍板。

## 4. 功能取舍清单

### 4.1 保留并强化

| 能力 | 现状 | 本轮动作 |

## 8. 分批实施

每批结束时都应有一个**能用的东西**，而不是一堆半成品。

| 批次 | 内容 | 解决的感受 | 结束时的可用状态 |

| **1** | Status/Scene 隐藏 + 筛选器加无状态条件 + 整理入口 | 看着庞大 | 界面变简单，浏览强度不减 |
| **2** | 全量检索 + 搜索结果直接操作 | 不完整、找不回 | 打开就搜全量，三秒找到并直接改 |
| **3** | 批量整理模式 + 回写状态可见性 | 整理不趁手 | 筛选 → 多选 → 改 → 看到回写结果，一条闭环 |

| **5** | 规则引擎（新收藏自动归类） | 整理不持续 | 一次配置，长期自动 |

批次 1 仍把「低成本瘦身」排在前面，因为它几乎零成本且立刻改善第一印象；但它**不再以「打开就能连上 Raindrop」为交付**，那是设置页的事。

## 9. 风险与代价（诚实列）

1. **单点依赖 Raindrop**：本定位下 Raindrop 不可用或 API 限流时，整理能力整体停摆。缓解：本地已拉数据仍可读可搜可批量编辑，只是回写排队。**决策五后这条风险降低**——浏览与查询不依赖 Raindrop，只有回写依赖。
2. **规则引擎会诱发新一轮膨胀**：规则本身容易长成「第二个分类系统」。约束：规则**只产出 Folder 与 Tag**，不产出 Scene。
3. **批量整理写错代价大**：一次批量操作影响几百条。缓解：回写前给影响面预览（将改哪几条、改成什么），回收站 + 撤销必须覆盖批量路径。
4. **OAuth 需要注册 Raindrop 应用**：一次性外部配置，不是纯代码工作。
5. **本轮不解决 Capture 侧的投入浪费**：保存表单、扩展、Skill API、快照引擎都还在，只是不再是唯一主轴。真正的取舍（删代码）在批次 4 之后再议。
6. **⛔ 修复本身可能误伤远端数据**：若 §0.5 待验证点 1 的答案是「PUT 为替换语义」，那么在补字段之前，**现有每次 update 都在冒清空远端收藏夹与标签的风险**。缓解：修之前先只读拉取（不推），确认无误再开写；或改走批量接口（字段语义明确）。**这一条需要在动手前解决。**
