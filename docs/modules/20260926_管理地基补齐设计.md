## 1. 专项一：标签改名与合并

### 现状问题
`TagManager` 只有新建/删除；Scene 与文件夹均有「编辑」。标签打错名只能删除重建，书签上的挂载全部丢失。

### 功能点
- **改名**：组织管理 → 标签，行内「编辑」（交互对齐 `FolderManager` 的编辑模式）。改名后所有书签上的该标签同步生效（标签按 id 挂载，天然同步）。
- **合并**：标签行新增「合并到…」操作，弹出选择目标标签；确认后源标签从系统消失，其全部挂载转移到目标标签；书签若同时挂有两者，去重只保留一条。合并前弹出确认框，讲清「此操作不可撤销」。
- 重名约束：改名撞已有 `name_key` 时报错并提示（沿用场景命名冲突的现有错误通道）；合并目标不能是自身。

### 技术方案
- 服务端：`PATCH /api/tags/:id`（改名，body `{name}`）；`POST /api/tags/:id/merge`（body `{targetId}`）。
- 合并实现为仓储层一个方法：`tags.merge(sourceId, targetId)`——`UPDATE bookmark_tags SET tag_id=target WHERE tag_id=source`，再删除 `tag_id=source AND bookmark_id IN (已存在 target 挂载)` 的重复行（或先查重复集再插，两侧方言都可用单条 `INSERT OR IGNORE` / D1 `INSERT ... ON CONFLICT DO NOTHING` 语义，落地时以 `packages/db` 既有去重写法为准），最后 `DELETE FROM tags WHERE id=source`。SQLite 与 D1 双实现。
- 操作日志：`rename_tag` / `merge_tag` 各记一条。
- 前端：`TagManager` 加编辑态与合并弹层；合并完成后 `notifyOrgChanged` 驱动侧栏/筛选下拉刷新。

### 验收
- 改名后筛选下拉、卡片 `#` pill、详情挑选器同步显示新名。
- 合并后：目标标签计数 = 原两者并集去重；源标签消失；操作日志两条。
- 两侧仓储单测：改名冲突 400、合并去重、合并后源删除。

## 2. 专项二：筛选/排序对齐定稿（§4.2.3）

### 缺口
- 筛选缺：**时间范围**、**是否在导航页展示**。
- 排序缺：**收藏标星**（现仅 recent/title/domain）。

### 功能点
- 工具栏排序下拉增加「收藏标星优先」（`sort=important`：important 优先，其余按时间倒序，同组内时间稳定）。
- 筛选行增加两个下拉：
  - **时间**：全部时间 / 最近 7 天 / 最近 30 天 / 最近一年（预设档，不做自由日期输入——避免为低频需求做日期选择器）。
  - **导航页展示**：全部 / 已在导航页展示 / 未在导航页展示。
- 新筛选与现有筛选、分页、搜索可叠加；筛选变更回第 1 页（沿用现有 keyset 口径）。

### 技术方案
- `GET /api/bookmarks`（及 `/search`）新增参数：`createdFrom` / `createdTo`（ISO 日期，服务端换算）、`navVisible`（`true|false`）、`sort=important`。均加性，旧调用不受影响。
- **navVisible 的实现取舍（需评审确认）**：「是否在导航页展示」不是字段，而是 `nav_rules` 求值结果。方案：筛选时服务端先跑一次既有求值器（`apps/server/src/nav/evaluator.ts`）得到展示集 id，再以 `IN` 集合过滤。代价是带该筛选的列表请求多一次求值查询；600 条基线下可接受。**不做**反向增量缓存（性能基线允许时再议）。
- 时间过滤直接落在 `bookmarks.created_at` 索引列，keyset 游标不受影响。
- 侧栏筛选、工具栏、分页器的既有联动逻辑复用，不改交互骨架。

### 验收
- 三参数组合 × 分页翻页无重复无漏项（回归上轮 EXISTS 修复口径）。
- `sort=important` 在有/无标星混合集上顺序正确。
- web 端纯函数测试：筛选参数组装。

## 3. 专项三：统计接口与侧栏准确计数

### 现状问题
侧栏各维度计数靠已加载列表近似（v0.7.15 注明「需统计接口」）；§4.2.8 统计类需求（状态分布等）无地基。

### 功能点
- 新增 `GET /api/stats`，一次返回：
  ```json
  {
    "total": 412,
    "byStatus": { "unread": 14, "saved": 351, "archived": 47 },
    "bySource": { "page": 380, "agent": 12, "extension": 15, "raindrop": 5 },
    "byScene":  [{ "id": "…", "name": "…", "count": 82 }],
    "byFolder": [{ "id": "…", "name": "…", "count": 120 }],
    "byTag":    [{ "id": "…", "name": "…", "count": 47 }],
    "importantCount": 23,
    "recycleCount": 6
  }
  ```
  口径：不含回收站与私密之外无特判；`byScene/byFolder/byTag` 全量返回（600 条基线下维度数量有限，不做分页）。
- 侧栏三个分区接入真实计数：每行右侧 mono 计数徽标（DM Mono、`--faint`→计数沿用原型琥珀口径，与 `ContentHead` 计数一致）。
- Inbox / 书签顶部导航计数同样取自该接口。
- 计数在组织维度变更（`onOrgChanged`）与书签增删后刷新；不做长轮询。

### 技术方案
- 服务端一组 `COUNT ... GROUP BY` 聚合查询（软删/私密过滤与 list 同口径），单路由 5~6 条聚合，Workers Free 子请求预算内。
- 前端新增 `api/stats.ts` + 轻量 store（`useSyncExternalStore`，与 `channel-tasks` 同款模式），避免每组件独立拉取。
- 侧栏行布局加计数徽标不改结构（flex 尾部对齐）。

### 验收
- 侧栏计数与筛选结果一致（按某场景筛选，计数 = 列表 total）。
- 删除/恢复/合并标签后计数即时正确。
- server 单测：各聚合口径（含软删排除）。

## 4. 视觉调整（2026-09-26 用户已确认，随本轮实施）

> 配套静态视觉稿：`docs/modules/20260926_管理地基补齐_视觉稿.html`（浏览器直接打开；上半为整体框架演示态、下半为筛选行三方向对比）。

已确认的口径：

1. **筛选行走方向 A**：全部筛选维度收进工具栏「筛选」弹层，单行内只占一个按钮（按钮上显示生效数，如「筛选 · 3」）；弹层内可查看与清除。
2. **ContentHead 整体去除**：不再有「书签 412 + 描述」标题区；计数由侧栏承担。
3. **工具栏压缩为单行**：搜索 / 筛选 / 排序 / 视图切换 / 添加书签（主按钮靠右）。原来源 chips 并入筛选弹层。
4. **场景视图适配**：激活场景时场景名以侧栏高亮承担；场景 AERR 主操作文案以 ghost 按钮并入工具栏行（无场景时不显示）。
5. **侧栏密度复核**：接入计数徽标后随专项三顺带对照原型复核行高与分组间距。
