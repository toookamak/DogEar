# 工作台外壳屏稿

本批范围：`apps/web` 的**应用外壳**——TopBar、Sidebar、StatusBar。外壳是所有页面共用的骨架，也是当前与原型差距最大的部分（正式 `AppShell.tsx` 27 行且无 TopBar）。外壳定下后，逐页推进时才有统一基准。

## 1. 已确认的三项口径

已与用户确认，作为本批前置约束：

| 项 | 决定 | 含义 |
| --- | --- | --- |
| 视觉源 | **以 `DESIGN.md` 为准** | 原型只提供页面结构、区块划分与交互；原型自成一体的配色/字体（`tokens.css` 的 `--amber`/`manrope` 等）**不采用** |
| 样式实现 | **class-based + CSS 样式层** | 消灭现状 307 处内联样式，建立 class 承载布局 |
| 开工顺序 | **先外壳（TopBar/Sidebar/StatusBar），再逐页** | 每页先出屏稿确认再写代码 |

## 2. 现状差距（事实，含出处）

### 2.1 结构

| 组件 | 原型 | 正式工程 | 差距 |
| --- | --- | --- | --- |
| 外壳 | `dev/dogear-workbench/src/components/layout/AppShell.tsx`（320 行，含 TopBar/内容头/工具栏/四视图/详情浮层/设置弹窗） | `apps/web/src/app/AppShell.tsx`（27 行：Sidebar + main + StatusBar） | **无 TopBar**、无内容头、无工具栏 |
| 侧栏 | `layout/Sidebar.tsx`（302 行，五段式） | `components/layout/Sidebar.tsx`（47 行，仅 6 条文本导航） | 缺统计卡、Scene、状态分组、标签云、底部动作 |
| 状态栏 | `layout/StatusBar.tsx`（72 行，含全套可观测指标） | `components/layout/StatusBar.tsx`（65 行，仅「未推送 N」+ 撤销） | 缺队列长度、条/秒、时延、成功率、429 |

导航项目前定义在 `apps/web/src/app/navigation.ts`（导航页 / Inbox / 书签 / 组织管理 / 回收站 / 设置）。

### 2.2 样式层（本批必须一并解决，否则新页面无处落脚）

- 正式工程组件共用 **307 处 `style={{}}`**，而 `className` 仅 120 处且**全仓只有 5 个类名**：`btn-primary`、`btn-secondary`、`btn-secondary-pill`、`card`、`input`。
- **`.btn-secondary` 从未定义**：被 20 个文件引用 40 次，但 `apps/web/src/styles.css` 只定义了 `.btn-secondary-pill` → 这些按钮当前**完全无样式**（例：`components/detail/BookmarkDetail.tsx:119`）。
- **6 个 CSS 变量被引用但未定义且无 fallback** → 样式静默失效：`--color-primary`、`--color-tag-bg`、`--color-success-bg`、`--color-error-bg`、`--color-error-text`、`--color-success-text`（另有 `--color-bg-card`、`--color-bg-warning-subtle`、`--color-text-warning` 三个带 fallback，暂不失效）。
- `apps/web/src/styles.css`（182 行）本身**忠实转录了 DESIGN.md**（`#f2f1ed`/`#26251e`/`#f54e00`/oklab 边框/三套字体栈/8px 与亚 8px 间距/圆角尺度），但组件基本不用它 → 问题不在缺规范，而在**缺承载规范的类**。
- 原型侧 `tokens.css` 含 6 套主题块，其中 4 套（claude / notion / claude-dark / notion-dark）已被原型自身标注为 `TODO(pending)` 待评审，且原型入口已收敛为 light/dark（`dev/dogear-workbench/src/App.tsx:10-32`）。**不照搬这些死重。**

### 3.3 StatusBar（补齐可用部分）

原型含：状态灯 + 阶段、上次同步、未推送数、队列长度、条/秒、时延、成功率、429 次数。

**本批块划分**：

| 位置 | 块 | 数据来源 | 状态 |
| --- | --- | --- | --- |
| 左 | 待同步数 | `syncApi.pendingCount()`（`sync_queue` 的 pending 计数） | 已实现 |
| 右 | 撤销 | 现有 `undo.ts` + `bookmarksApi.revert()` | 已实现（改为 `notifyDataChanged()` 局部刷新，去掉整页 reload） |
| 右 | 条/秒、时延、成功率、429 | **无接口** | 本轮不做，见 §4 |

- **空状态**：无（状态栏常驻）。
- **本轮不做**过度设计：不引入状态灯动画、不做阶段文案机。
- **实现修正**：原型把「未推送数」与「队列长度」列为两项，但正式后端这两个值**同源**——`GET /api/sync/pending-count` 即 `sync_queue` 的 pending 计数，而 `GET /api/sync/queue` 返回的是同一批 pending 条目（且带 `limit`，默认 50，不返回总数）。故合并为一项「待同步 N」，不重复展示同一数字，也不拿被 `limit` 截断的条数冒充队列长度。

## 4. 数据来源与现实约束（本批最大约束）

原型展示的许多数字**在后端没有对应接口**，必须如实标注，不能凭空造。

| 界面元素 | 原型 | 现有接口 | 结论 |
| --- | --- | --- | --- |
| 未推送数 | 有 | `GET /api/sync/pending-count` | **可做** |
| 队列长度 | 有 | `GET /api/sync/queue` | **可做** |
| Scene / 文件夹 / 标签**列表** | 有 | `GET /api/scenes`、`/api/folders`、`/api/tags` | **可做** |
| Scene / 文件夹 / 标签**计数** | 有 | 列表接口不返回计数 | 无接口 |
| 状态计数（待处理/已确认/搁置） | 有 | **无工作台端点** | 无接口 |
| 条/秒、时延、成功率、429 | 有 | **全无** | 无接口 |

补充事实（影响判断）：

- 存在 `get_stats`，但它是 **Skill 接口**（`apps/server/src/app.ts:690`），挂在 `app.use('/api/skill/:name', requireSkill)`（同文件 600 行）之下，为 **Bearer 鉴权**，工作台走 Cookie 会话，**不能直接调用**。
- 即便接上，该实现也不适合作计数来源：`app.ts:694` 用 `repository.list()` **读全量书签后在内存里 filter** 计数，且 `scenes` 恒返回空数组 `[]`（同文件 695 行）。这与「列表接口不得先读全量」的性能基线（`docs/API结构表.md` 第 316 行）冲突，在 600 条基线下不划算。
- `docs/API结构表.md` 第 31 行明令「升级规则…**禁止边写代码边加路由**」→ 新增工作台统计端点属于**后端范围 + 需先升 API 结构表版本**，不在本批前端工作内。

**计数元素的处理选项**：

- (a) **本轮不做计数**：侧栏只列维度名，不显示数字。纯前端、零后端改动、不产生错误数据。**推荐**。
- (b) 新增工作台统计端点（如 `GET /api/stats`）：需先讨论并升 `docs/API结构表.md` 版本，另立环节。
- (c) 客户端用现有分页接口自行累计：不准确，且违背上引性能基线。**不建议**。
