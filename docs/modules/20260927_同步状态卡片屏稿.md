# 同步状态胶囊 · 屏稿

## 1. 背景

用户诉求（2026-09-27）：Raindrop 内容感觉不同步，希望页面上有一处能看到同步状态，并有「拉取」「推送」按钮。此前：

- 拉回（Raindrop → DogEar）是纯手动且入口只在设置页，每次仅 1 页 50 条；
- 推送失败的条目（重试 8 次后留队）在界面上不可见——「待同步 N」只数 pending；
- 没有任何「上次同步时间」记录，无从判断是否同步过。

## 2. 触发方式与位置（v1.1 重写）

**折叠态**：顶栏右缘的同步胶囊（`.syncbox` → `.sync-lamp`），三色灯箱 + **常驻积压数**。

- 灯箱三格固定自左向右为 **红 / 黄 / 绿**，同一时刻最多亮一格：
  | 灯态 | 含义 |
  | --- | --- |
  | 绿常亮 | 数据一致（无待推送、无失败） |
  | 黄常亮 | 有修改未同步（`pendingPush > 0`） |
  | 黄绿交替 | 正在同步（拉取 / 推送进行中），优先于其它态 |
  | 红闪烁 | 出错——队列里有推不过去的条目（`failedPush > 0`）**或**上一次拉取 / 推送直接失败（v1.2 补，典型是本地没配通道被服务端 400 拦下） |
- 积压数取 `pendingPush`，即「还剩多少条没推上去」。这是对方案 D 的**有意偏离**：方案 D 折叠态只有灯、无文字，会退化成「要点开才知道有没有积压」，比原状态栏的常驻「待同步 N」更差。
- 数字着色：红灯态用 `--red`、绿灯态用 `--mint`、黄灯态用中性 `--muted`（黄字在浅底上对比不足）。
- 读取失败时积压数显示 `—`，不显示假的 `0`——此前失败被 catch 吞掉，用户会把「取不到」误读成「没有待同步」。

**展开态**：悬停或点击胶囊，浮条从胶囊**左侧**滑出（`.sync-strip`）。

- 方向为**向左生长**：靠 `justify-content: flex-end` 让内容贴住右缘，宽度由 `max-width: 0` 增长时最右侧先出现、左侧后出现。若用默认 `flex-start` 会读成向右展开。
- 点击为**钉住**（`is-open`），悬停不留住、移开即收；点浮条外任意处或按 Esc 收起（`mousedown` 而非 `click` 监听，避免「点开又立刻关上」）。
- 收起态用 `visibility: hidden` 而非仅 `opacity: 0`：否则键盘 Tab 仍会聚焦到看不见的「拉取 / 推送」。
- **宽度预算**：浮条展开最大 380px，占顶栏中段空档。顶栏空档 ≈ `(视口宽 − 599px) / 2`，故顶栏搜索上限由 420px 收到 320px 让位。视口 `< 1366px` 时空档不足，浮条退化为**右锚定、落在顶栏下沿之下**（仍自右向左生长，但不压搜索入口）。

## 3. 浮条结构（v1.1 重写）

```
                        ┌─ 同步状态（Raindrop）────────────────────────────┐
        ……（顶栏）…… │ [拉取] [推送]  待推送 3  失败 1  上次 12 分钟前 │  ●●●  3 │
                        └─────────────────────────────────────────────────┘
```

- **拉取**（`.btn--pill`）：单页低频拉回（50 条，防 Raindrop 风控），与设置页「拉取」同语义；进行中禁用并显示「拉取中…」。
- **推送**（`.btn--pill.btn--primary`）：循环调用 `POST /api/sync/process`（每轮最多 10 条），直到 `remaining === 0`、达 **20 轮上限（约 200 条）** 或本轮 `processed === 0`（剩余全是退避未到期的失败项，继续只会空转）；进行中禁用两按钮并显示「推送中（第 x 轮）」。
- **待推送 N**：`sync_queue` pending 计数（与折叠态同源）。
- **失败 N**：`sync_queue` failed 计数。>0 时红字，并带 `title` 说明「失败条目按退避自动重试（最多 8 次），超限后需人工排查」——完整说明放 `title` 是因为单行浮条塞不下，硬塞会把「拉取」挤出可视区。
- **冲突 N + 管理冲突 →**：`pendingConflicts > 0` 时渲染，琥珀色，跳 `/settings?tab=channels`。
- **上次同步 {相对时间}**（v1.2 修正）：`lastSyncAt = max(lastPushAt, lastPullAt)`，即推送与拉取中较晚的一次；精确拆分放 `title`（「上次推送：X · 上次拉取：Y」）——浮条单行放不下两行时间。**v1.1 曾只显示 `lastPushAt` 且标签写「上次」，导致用户点完「拉取」仍看到「从未」，读起来像功能坏了**，故连同标签一并改为「上次同步」。
- **上次操作失败**（v1.2 新增）：`actionError` 非空时以红字渲染，失败原因放 `title`。它由拉取/推送的 catch 写入、下次成功即清空；因为会一直留到下次成功，标签写「上次」而非裸「操作失败」，以免被读成当下的故障。
- **读取失败态**：浮条内显示「同步状态读取失败」+「重试」按钮，而非整条隐藏。
- **动效约束**：黄绿交替与红闪烁属状态类循环动画，不受项目「过渡只有两档（150/200ms）」的约束，但**必须**在 `prefers-reduced-motion: reduce` 下关闭（已实现）。

## 3.1 v1.0 形态与迁移原因

v1.0 的卡片挂在 28px 底部状态栏的「待同步 N」上，点击向上弹卡片。迁到顶栏有两条原因：

1. **状态栏是最下沿，离主视线最远**——同步状态是常驻状态，不该放这里；
2. **同屏重复**——顶栏已有常驻状态区，两边各放一个同步入口，与「顶栏和工作台各有一个添加书签」是同一类问题。

迁移后状态栏只留**瞬时任务**（通道导入 / 导出进度、撤销入口），空闲时基本为空。v1.0 的「弹出卡片」形态**废弃**，不再保留为备选。

## 3.2 「上次同步」与「上次操作失败」的语义裁决（v1.2）

浮条只有一行、宽上限 380px，必须裁掉冗余信息。三处取舍：

| 取舍 | 结论 | 理由 |
| --- | --- | --- |
| 「上次」是推送时间还是拉取时间？ | **两者取较晚者，标签写「上次同步」** | 拉取与推送是同一排的两个按钮，紧邻的「上次」必然被读成「上次我做的那个动作」。只取推送时间会在刚点完拉取时显示「从未」 |
| 是否分两行展示「上次推送 / 上次拉取」？ | **不分行，拆分进 `title`** | 单行浮条放不下；两行会把胶囊从「一眼看到积压」退化成「要读两行」 |
| 拉取/推送失败的原因是否常驻上屏？ | **常驻，但只显示「上次操作失败」四字** | 完整文案约 20 字，上屏会把「拉取」按钮挤出可视区；而只靠 toast 不够——错误 toast 6 秒后消失、界面不留痕，用户回头只看到「从未」，会以为功能坏了（2026-09-27 用户反馈即此类） |

**已知代价**：「上次同步」在只拉取过的情况下也显示时间，理论上会让「我的改动推上去了没」这一问失去直接答案。之所以可接受：`failedPush > 0` 与 `pendingPush > 0` 分别以红字「失败 N」和「待推送 N」独立呈现，推送侧的状态没有被这个字段掩盖。

## 4. 后端配套（本轮最小改动）

- 新增 `GET /api/sync/status`：`{ pendingPush, failedPush, pendingConflicts, lastPushAt, lastPullAt }`，一次请求替代前端三次探测。
- `packages/db`：`syncQueue.countFailed()`（failed 计数，纯查询，无 schema 变更）。
- 时间戳写入点三处：`POST /api/sync/process`（succeeded>0）、Workers Cron `scheduled`、自托管定时器；拉取在 `POST /api/sync/pull` 成功后写。均写 `settings` 表，不动表结构。

## 5. 不做

| 不做 | 原因 |
| --- | --- |
| 浮条内展示失败条目明细/单条重试 | 本轮只给计数；明细排查仍走队列接口，需要时另立批次 |
| 自动拉回（Cron 拉取） | 同步设计 §3.2 明确不做，防 Raindrop 风控 |
| 拉取翻页循环 | 每次 50 条由用户决定是否继续，保持低频约束 |
| 失败条目一键清除 | 涉及数据删除，先不进界面 |
