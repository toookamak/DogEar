# 状态栏同步状态卡片 · 屏稿

## 1. 背景

用户诉求（2026-09-27）：Raindrop 内容感觉不同步，希望页面上有一处能看到同步状态，并有「拉取」「推送」按钮。此前：

- 拉回（Raindrop → DogEar）是纯手动且入口只在设置页，每次仅 1 页 50 条；
- 推送失败的条目（重试 8 次后留队）在界面上不可见——「待同步 N」只数 pending；
- 没有任何「上次同步时间」记录，无从判断是否同步过。

## 2. 触发方式与位置

- 底部状态栏的「待同步 N」升级为**可点击项**（hover 有浅色底提示可点）。
- 点击弹出**向上展开**的同步状态卡片（状态栏在最底部，弹层只能朝上）；点击卡片外任意处或再次点击收起。
- 读取失败时保持既有「同步状态读取失败 + 重试」形态，不弹卡片。

## 3. 卡片结构

```
┌─ 同步状态（Raindrop）──────────────┐
│  待推送 3 · 推送失败 1 · 待处理冲突 2 │
│  上次推送 09-27 08:31               │
│  上次拉取 09-26 22:10               │
│  ───────────────────────────────── │
│  [拉取]  [推送]        管理冲突 →   │
└────────────────────────────────────┘
```

- **待推送 N**：`sync_queue` pending 计数（数据源不变）。
- **推送失败 N**：`sync_queue` failed 计数（新增口径）。>0 时红色；卡片内该行加一句提示「失败条目会在退避后自动重试（最多 8 次），超限后需人工排查」，推送按钮会先把退避到期的失败项重置回队列再消费。
- **待处理冲突 N**：conflicts pending 计数。>0 时琥珀色，附「管理冲突 →」链接跳设置页冲突面板；为 0 时不渲染该链接。
- **上次推送 / 上次拉取**：服务端在推送消费成功 / 拉取完成后写入 `settings` 表（key：`sync.last_push_at` / `sync.last_pull_at`），格式 MM-DD HH:mm；无记录显示「—」。
- **拉取**：单页低频拉回（50 条，防 Raindrop 风控），与设置页「拉取」同语义；进行中禁用并显示「拉取中…」，完成后 toast 汇总（新增/冲突/hasMore），并刷新卡片。
- **推送**：循环调用 `POST /api/sync/process`（每轮最多 10 条），直到 `remaining === 0` 或达 **20 轮上限（约 200 条）**；进行中禁用两按钮并显示「推送中 x 轮」；完成后 toast「成功 X / 失败 Y，剩余 Z」并刷新卡片。未配置 Raindrop 通道时点击返回错误 toast，不崩。
- 卡片内数字与状态栏项同源同刷新（30s 轮询保留）；操作完成后立即重取一次。

## 4. 后端配套（本轮最小改动）

- 新增 `GET /api/sync/status`：`{ pendingPush, failedPush, pendingConflicts, lastPushAt, lastPullAt }`，一次请求替代前端三次探测。
- `packages/db`：`syncQueue.countFailed()`（failed 计数，纯查询，无 schema 变更）。
- 时间戳写入点三处：`POST /api/sync/process`（succeeded>0）、Workers Cron `scheduled`、自托管定时器；拉取在 `POST /api/sync/pull` 成功后写。均写 `settings` 表，不动表结构。

## 5. 不做

| 不做 | 原因 |
| --- | --- |
| 卡片内展示失败条目明细/单条重试 | 本轮只给计数；明细排查仍走队列接口，需要时另立批次 |
| 自动拉回（Cron 拉取） | 同步设计 §3.2 明确不做，防 Raindrop 风控 |
| 拉取翻页循环 | 每次 50 条由用户决定是否继续，保持低频约束 |
| 失败条目一键清除 | 涉及数据删除，先不进界面 |
