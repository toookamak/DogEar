# DogEar · 技术方案路线（v0.3）

> 实施级方案，关联 PRD v0.3.8、部署方案 v1.0、同步引擎细化 v0.2 与 600 条基线。
> 本版已落定部署双轨、服务端真源、同步边界与运行时选择。

## 0. 推荐组合（已确认方向）

- **部署**：Cloudflare Workers + D1 为默认轨；Docker + SQLite 为本地轨，同一套 Hono 业务代码，二选一互不级联

- **存储**：服务端 D1/SQLite 为真源，各端 IndexedDB 为缓存；不再采用前端直连 Raindrop 作为 MVP 主路径

- **Docker 运行时**：Bun，使用 `bun:sqlite`，通过 `packages/db` 适配器隔离运行时差异

- **前端**：Vite + React + 虚拟列表（600 条分页）

- **扩展**：Chrome 扩展（MV3 新标签页）与工作台同域，共享存储

- **Skill API**：与本地服务同域，`/.well-known/capabilities` 自描述，Bearer Token

```
工作台（Vite+React）─┐
                      ├─→ 本地服务（Hono）─→ 同步引擎 ─→ Raindrop（备份/跨端兜底）
导航页（Chrome扩展）─┘         │
                           存储抽象层
                      ┌──────┴──────┐
                 Workers: D1（服务端真源）   Docker: SQLite（服务端真源） + IndexedDB（各端缓存）
```

## 1. 存储详述（核心）

### 1.1 IndexedDB — 浏览器端缓存

- **位置**：浏览器内的本地数据库，跟随“哪个浏览器”走

- **优点**：零后端、读写即时（点一下就生效）、实现最快

- **缺点**：仅单设备/单浏览器可见；清浏览器数据会丢（靠 Raindrop 恢复）；多端需靠 Raindrop 对账

> 类比：手机相册“仅本机保存”，换手机靠云备份恢复。

**端侧数据流：**

```
工作台/导航页 ↔ IndexedDB（缓存） ↔ 服务端 API ↔ D1/SQLite（真源）
                                             ↕
                                      同步引擎 ↔ Raindrop
```

### 1.2 SQLite + IndexedDB 缓存 — Docker 轨服务端真源

- **SQLite**：跑在服务器上的轻量数据库文件（一个 `.db` 即全部数据），事务稳，适合做中央账本

- **组合不是二选一，是分层**：

  - **服务端 SQLite = 真源（中央账本）**

  - **各端 IndexedDB = 缓存（本地副本，断网也可用）**

```
设备A IndexedDB ─┐
                  ├─→ 服务端 SQLite（真源） ─→ Raindrop（兜底备份）
设备B IndexedDB ─┘          ↑
                    工作台/导航页都经存储抽象层访问
```

- **优点**：多端共享服务端真源（A 改完写入服务端，B 拉取缓存）、可做完整快照（对应“重备份”）、仍保持端侧缓存优先（无网可读，联网对账）

- **缺点**：需一台服务器与鉴权运维

> 类比：微信聊天记录 — 本地有缓存，服务器是中央记录，换设备拉取即可。

### 1.3 服务端真源与端侧缓存的分层

| 部署轨     | 服务端真源  | 端侧职责                |
| ------- | ------ | ------------------- |
| Workers | D1     | IndexedDB 作为首屏与离线缓存 |
| Docker  | SQLite | IndexedDB 作为首屏与离线缓存 |

**抽象层示例（接口不变）：**

- 上层：`storage.save(bookmark)` / `storage.search(query)`

- Workers 轨：通过 D1 适配器读写服务端真源

- Docker 轨：通过 SQLite 适配器读写服务端真源

- 两轨均由端侧 IndexedDB 提供首屏缓存与离线读取

**600 条影响**：两种形态在 600 条下性能无差别，差异只在多端与备份完整度；配合虚拟列表/分页，搜索均为毫秒级。

**与备份的对应**：轻（业务数据导出 HTML/CSV/MD）→ 中（+配置）→ 重（服务端全量 JSON bundle 或 SQLite 快照，含 log/queue）

## 2. 前端

- Vite + React 为主，组件与扩展复用

- 600 条采用虚拟列表/分页，搜索本地索引（标题/url/tags/备注），不做全文正文索引

## 3. 后端/同步

- **服务端 Hono**：Workers 轨运行在 Cloudflare workerd，Docker 轨使用 Bun；同步引擎顺序消费 + 指数退避

- 推送 30s 合并窗口、拉取默认 5min，支持 15min/手动配置

- 拉取先按 collection 的 `lastUpdate` 做增量探测，变化时才分页获取详情；首次初始化和每周兜底才做全量

- 冲突两端保留，提供“用本地/用远端/手动合”视图；429 限频不阻塞本地

- Worker 轨不绑定 KV；强一致游标、队列与退避状态进入 D1，KV 仅预留给未来边缘缓存或多实例场景

## 4. Chrome 扩展

- MV3 `chrome_url_overrides.newtab` 替换新标签页

- 与工作台同域则共享 IndexedDB，跨域则经 `chrome.storage` + 消息桥（MVP 同域最简）

- favicon 抓取缓存，降级首字母；Docker/页面标签为本地配置不进 Raindrop

## 5. AI Skill

- `/.well-known/capabilities` 自描述，Bearer Token，限速

- 记忆存服务端 `ai_memory`，在 `设置 > AI` 预览/重置，日常仅需 Token 即可

## 6. 性能与监测

- 导航页可开关以降低开销；非核心计算延后/降频

- 导入导出/备份异步化

- **同步速率监测（新增）**：记录服务端真源与 Raindrop 之间的数据同步速率，方向性指标包括：推送/拉取条数/秒、平均时延、成功率、队列长度与重试次数、限频触发次数；数据可在日志/设置中查看，用于 600 条基线下的性能考核与后续调优

## 7. 已定结论

- 存储抽象由 `packages/db` 隔离 D1 与 SQLite，服务端为真源，IndexedDB 为端侧缓存

- 同步默认推送合并 30 秒、拉取 5 分钟，支持 15 分钟与手动模式；频率与重试参数可配置

- 冲突保留两端数据并由用户选择处理，不采用自动覆盖

- Docker 使用 Bun；KV 预留但不默认绑定

> 具体接口与验收以部署方案、同步引擎细化和数据模型为准。
